9. 8 条指导原则

本节从 PI 批判 + OpenBuddy 能力盘点 + 本 change 实施过程中提炼出 8 条指导原则。后续 P1 / P2 阶段均应遵循这些原则，避免重蹈 PI 文档族「主语偏差」「验证集中」「LOC 净下降等同商业价值」的覆辙。

原则 1 · 主语反转

所有「改造 / 验收 / 路线图」类文档主语必须为 OpenBuddy 产品 / 用户 / 客户 / 销售 / 企业 admin，而非 Pi / Pi extension / Pi session / Pi-native。仅当 Pi 原生契约与产品需求一致时才引用 Pi。

原则 2 · 验收分层

验收必须覆盖 IPC / 工程 / UX / 商业 / 企业 / 多租户 / 数据安全 / 跨平台 / 长会话 9 维度，禁止「单 LLM MiniMax 5 轮 smoke = 完整产品验证」。Pi 集成 ≠ 产品可用。

原则 3 · 价值 ≠ LOC

LOC 是工程指标不是用户价值。用户看到的价值 = UX 提升 + 新功能 + 商业权益 + 续费 / 推荐 / NPS。禁止用 LOC 净下降作为成功标志。

原则 4 · 数据权威分层

SQLite 是结构化状态和事件的 system of record；Pi JSONL 是 transcript 兼容 / 审计导入源；Keychain 是凭据权威源。三层明确分离，禁止越层读写。

原则 5 · 多租户 / RBAC / SSO 不可缺

所有新功能必须经过多租户边界探针（verify-tenant-boundaries.sh 9 probe）+ Casdoor tenant context + RBAC 校验。PI 假设单进程模型不适用于多租户场景。

原则 6 · 商业账本独立

Wallet / Credit / Ledger / Order / SKU / 退款 / 过期流水归 Resource Gateway 25+ handle* 端点管理，Cordis 不替代商业账本事实源。BYOK 是其中一个维度，不是全部。

原则 7 · WorkBuddy 不伪造

严格遵循 workbuddy-parity-matrix.md:11「未实现、未伪造、不纳入真实通过项」。禁止基于推测实现 inspiration / 团队 / 技能 / marketplace。

原则 8 · brief 不允许空模板

docs/comet/changes/<name>/brief.md 任一章节为空时拒绝提交（CI / pre-commit 守护）。空 brief 会让 Outcome / Scope / Acceptance / Verification 全部丢失。
