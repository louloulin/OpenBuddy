## §0 结论先行

1. **OpenBuddy 不缺功能，缺"秩序"。** 对话、审批、分支、产物工作台、排队、语音、@ 引用、`+` 菜单都有，但样式分散在 6 个 CSS 文件、18,857 行（`app.css` 一个文件 13,802 行），混用 `--wb-` / `--ob-` / `--atm-` / `--grok-` / `--md-` 五套变量前缀，`grok.css` 作为最后加载的覆盖层在改其他人的样式。界面"丑"的根源是没有唯一的设计系统，而不是缺某个组件。
2. **回合内信息噪音大。** 思考、每个工具调用、计划、子 agent、错误各自成卡，长任务会刷出几十张卡片。Lumos 与 Grok Bot 都把"思考 + 工具调用"压成**一行按时间顺序的叙述**，点开才看细节；WorkBuddy 则用约 200 条"阶段 × 工具"进度文案，信息密度低。这里是最容易超越 WorkBuddy 的点。
3. **没有通用的生成式 UI。** 现有富卡片（金融卡、应用推荐卡、应用安装确认卡等）全部按工具硬编码；`packages/chat-core/src/tool-renderers.ts:21` 已经预留 `visualizer` 渲染器类型却没接入渲染链路。WorkBuddy 有 `show_widget` + `widget_guidelines`；Lumos 有白名单 A2UI 协议但只用在 A2A 任务详情。本计划把 **AI2UI（兼容 Google A2UI 消息格式的白名单声明式 UI）** 接入主聊天流，作为所有富卡片的统一底座。
4. **"更简单"的具体含义**：首屏只有一个输入框；控件按状态出现（空输入只有麦克风，打字后才有发送）；一个强调色；所有"需要你决定"的事项用同一种卡片，答复后收起成一行；模式靠意图推荐而不是让用户先理解 Craft / Plan / Ask 的区别。
5. **执行顺序**：先重建设计系统（M0），再改回合呈现（M1），然后接 AI2UI（M2），再做输入框和导航（M3），最后做产物面板、性能和打磨（M4–M5）。每个里程碑都能单独发布，并且有 `electron-ui-check.mjs` 断言锁住实测值。

## §3 当前 AI Chat 存在的问题（按影响排序）

### 3.1 视觉层
- **P-V1 样式体系分裂**：`apps/web/src/styles/` 下 `app.css`（13,802 行，1657 行起自带 `:root`，1680 行起自带暗色块）、`polish.css`（1,549）、`automation-wb.css`（1,925）、`grok.css`（714，最后加载的单色覆盖层）、`chat.css`（633）、`composer-wb-align.css`（234）。同一元素的最终样式要跨 3–4 个文件才能确定，任何改动都可能被后加载的文件覆盖。
- **P-V2 令牌前缀混用**：`--wb-` 约 4,031 处、`--ob-` 596、`--atm-` 229、`--grok-` 143、`--md-` 若干；还有硬编码兜底色（`app.css:12247` 的 `#ff8a8a`、`12312` 的 `#4ade80`）。
- **P-V3 层级不清**：卡片、气泡、工具卡、计划面板都用边框 + 背景 + 阴影，视觉权重相同，用户找不到"现在该看哪里"。
- **P-V4 无"跟随系统"主题**，暗色规则散落（`polish.css` 内 36 条暗色规则、`grok.css:58` 起又一套）。

### 3.2 回合与信息架构
- **P-I1 工具卡刷屏**：`shared/agent-ui/ToolCallCard.tsx:64` 每个调用一行卡片，20 步任务就是 20 行；思考块、计划面板（`features/chat/PlanPanel.tsx` 456 行）、子 agent 卡（`ChatView.tsx:656`）再各占一块。
- **P-I2 "在做什么"不清楚**：流式期间只有 LoadingRow 和平滑文本，没有"动词 + 已用时 + token 数"的状态行，长任务看起来像卡住。
- **P-I3 决策事项分散**：权限卡、提问卡、计划确认、应用安装确认（`features/apps/AppInstallConfirm.tsx:21`，目前只在 `AppsPanel.tsx:280` 使用）样式和位置各不相同，答复后仍以完整卡片留在消息流里。
- **P-I4 回合尾缺收束**：没有"本回合改了哪些文件 / 产出哪些产物"的摘要，也没有追问建议。

### 3.3 输入框
- **P-C1 控件常驻**：模型、权限、工作区、语音、上下文用量、`+` 全部常驻，空输入框也显得拥挤（`features/composer/Composer.tsx` 698 行）。
- **P-C2 `@` 引用是纯文本**：引用插入后无法一眼区分、不能点开看详情、删除要逐字删。
- **P-C3 模式需要先理解**：用户必须知道何时切 Plan，没有基于意图的提示。

### 3.4 生成式 UI
- **P-G1 无协议**：每种富卡片都要改 TurnView 加分支（如 `AppRecommendCard` 在 `TurnView.tsx` 约 257 行硬编码），模型无法按需组合 UI。
- **P-G2 死代码**：`detectToolRenderer`（`tool-renderers.ts:49`）只有测试调用；扩展 UI 的 `setWidget`（`packages/engine/src/extension-ui/bridge.ts:178`）只能显示文本行。

### 3.5 性能与可靠性
- **P-R1 非虚拟化**：`chat-view/transcript-metrics.ts` 的 `RENDER_WINDOW=30` 是分块挂载，几百回合时 DOM 仍然膨胀；mermaid/katex 在流式中反复解析。
- **P-R2 单条消息渲染异常会影响整页**：没有按消息的错误边界。
- **P-R3 焦点管理只在设置面板确认**（`SettingsPanel.tsx:134`），其他弹层未逐个核查。

## §4 设计原则

1. **一个输入框起步**：首屏、空会话、新任务都只有居中输入卡和最多 4 张启动建议。
2. **控件按状态出现**：空输入只有麦克风和 `+`；有内容才出现发送；流式中发送位变停止；模型/权限收进一个"会话设置"胶囊。
3. **默认收起，按需展开**：思考、工具、子 agent 合成一行；详情进抽屉或右侧面板。
4. **一个强调色**：只给主操作、选中态、未读与焦点环；状态色（成功/警告/错误/信息）独立，不与强调色混用。
5. **需要你决定的，只有一种样子**：决策卡统一外壳，停靠输入框上方，答复后在消息流里收起为一行记录。
6. **模型能画 UI，但画不出危险**：AI2UI 只接受白名单组件，按钮不直接执行写操作，动作回传为一条用户可见的消息或经审批的工具调用。
7. **每个视觉断言都锁进实机走查**：改动以实测值写入 `apps/desktop/scripts/electron-ui-check.mjs`。

## §7 M1 回合呈现重做（最直接的"变好看"）

### 7.1 活动行（ActivityLine）
把一个助手回合内、两段正文之间连续出现的思考、工具调用、子 agent 调用合并成一个"活动组"，渲染为一行叙述。

- **模型**：新增 `packages/chat-core/src/activity-group.ts`
  - 输入：回合的有序 parts；输出：`Array<TextSegment | ActivityGroup>`。
  - `ActivityGroup = { steps: Step[]; status: 'running'|'done'|'error'; durationMs; summary: SummaryItem[] }`。
  - 摘要按动作归类计数并保持首次出现顺序：`思考 12s · 读取 3 个文件 · 编辑 2 个文件 · 运行 1 条命令 · 搜索 2 次 · 委派 1 个子任务`。归类复用 `detectToolRenderer`（`tool-renderers.ts:49`，借此把死代码接入链路）。
  - 有失败步骤时摘要末尾追加 `· 1 步失败`，用 `--ob-danger` 色。
- **组件**：`apps/web/src/features/chat/activity/ActivityLine.tsx`、`ActivityStepList.tsx`
  - 收起态：一行，左侧状态图标（运行中为细旋转环，完成为淡色勾），文字 `--ob-text-sm` + `--ob-fg-secondary`，无边框无背景。
  - 展开态：步骤列表，每步一行，复用 `ToolCallCard.tsx:64` 的单行布局但去掉卡片边框；点击打开现有 `ToolCallDetailBody`（`ToolCallCard.tsx:118`）抽屉。
  - 思考步骤展开后显示全文（沿用 `TurnView.tsx:52-97` 的逻辑与页内搜索自动展开 `TurnView.tsx:82`）。
  - 子 agent 步骤显示子任务标题与状态点，点开跳到右侧"大纲"面板对应 tab。
- **规则**：运行中的组默认展开最后 1 步的实时输出（命令输出最多 6 行尾部滚动）；回合结束后 600ms 自动收起；用户手动展开过的组不再自动收起。

### 7.2 流式状态行（StreamingStatus）

## §8 M2 AI2UI：主聊天流的生成式 UI

### 8.1 目标与边界
- 模型可以用声明式 JSON 描述一块 UI（表单、表格、图表、指标卡、步骤、选择题），宿主用白名单组件渲染，用户的操作以结构化动作回传给模型。
- **不是** HTML 渲染：可执行的 HTML/JS 只能走 §10 的沙箱 artifact。AI2UI 组件里没有任何可执行内容。
- 兼容 Google A2UI 消息格式（`beginRendering` / `surfaceUpdate` / `dataModelUpdate` / `deleteSurface`，组件写法 `{component:{Text:{text:{literalString}}}}`），同时接受 Lumos 式扁平写法 `{version:1, root, components:[{id,type,...}]}`。这样 A2A 对端（`peer:` 节点）发来的 A2UI 也能直接渲染。

### 8.2 协议（`packages/protocol/src/ai2ui.ts`）
```ts
export const AI2UI_MIME = "application/vnd.openbuddy.ai2ui+json";
export interface Ai2uiSurface {
  version: 1;
  surfaceId: string;            // 同一 surfaceId 的后续消息是增量更新
  title?: string;
  root: string;                 // 根组件 id
  components: Ai2uiComponent[]; // 扁平邻接表，children 用 id 引用
  dataModel?: Record<string, unknown>; // 表单初始值，组件用 JSON Pointer 绑定，如 "/form/region"
  catalog?: "core" | "ob";      // ob 为 OpenBuddy 扩展组件目录
}
export type Ai2uiAction = { surfaceId: string; name: string; payload?: unknown; data?: Record<string, unknown> };
```
- **组件白名单（core）**
  - 布局：Column、Row、Card、Divider、Tabs、List。
  - 内容：Text（纯文本）、Heading、Markdown（经现有 rehype-sanitize）、Badge、Icon（lucide 名白名单）、Image、KeyValue、Stat（指标 + 同比箭头）、Progress、Steps、Alert。
  - 数据：Table（排序、列格式 number/currency/percent/date）、Chart（line/bar/area/pie/scatter）。
  - 输入：TextField、TextArea、Select、Checkbox、RadioGroup、Slider、DateField、Button。
- **扩展目录（ob）**：把现有硬编码卡片注册为命名组件：`ob:FinanceQuote`（`FinanceDataCards`）、`ob:AppRecommend`（`AppRecommendCard`）、`ob:AppInstall`（`AppInstallConfirm`）、`ob:FileRef`、`ob:EmailDraft`（可编辑草稿卡，借鉴 Grok Bot `email-draft.tsx`）。TurnView 里的硬编码分支删除，统一走注册表。
- **硬上限**：组件 ≤ 128、嵌套深度 ≤ 8、单容器子节点 ≤ 32、payload ≤ 128 KB、Table ≤ 500 行、Chart ≤ 2,000 点、文本单字段 ≤ 8 KB。超限截断并在卡片底部显示"内容过多，已截断"；未知组件类型丢弃并在开发者模式下提示。
- **图片来源**：只允许 `data:image/*`、工作区文件（经主进程 `ob-file://` 协议并校验在工作区内）、以及设置中开启"允许远程图片"后的 https；默认不加载远程图片，防止跟踪像素。
- **链接**：Text/Markdown 内链接点击经 `shell.openExternal` 前确认，不允许 `javascript:`/`file:`。

### 8.3 动作回传
| 动作类型 | 触发 | 宿主行为 |
|---|---|---|
| `submit`（默认） | Button `action.name` | 收集 `dataModel` 中被引用的字段，生成一条用户消息：可见部分是一枚胶囊"提交了『筛选条件』：区域=华东，季度=Q3"，结构化部分作为 `ai2ui_action` part 发给模型；卡片随后变为只读"已提交"态 |
| `tool` | Button 声明 `action.tool` | 只允许调用已注册工具，走现有权限系统（会弹 DecisionCard），不绕过沙箱/审批 |
| `local` | 本地 UI 行为：切 Tab、展开、复制、导出 CSV/PNG | 纯前端处理，不发消息 |

- 防重放：每个 surface 的 submit 只能成功一次（可由模型发新 surface 重开）；按钮点击后立即禁用直到回执。
- 会话重载后，surface 与 dataModel 从消息 parts 恢复；已提交的保持只读。

### 8.4 模型如何产出 AI2UI
1. **内置工具 `ob_render_ui`**：`packages/engine/src/builtin/render-ui.ts`，与 `app-recommend.ts` 同模式在 `builtin/index.ts` 注册。入参是 `Ai2uiSurface`，JSON Schema 由 `packages/protocol/src/ai2ui.ts` 生成（单一来源）。工具结果返回"已渲染 / 校验错误列表"，校验失败时模型可自行修正重试。
2. **代码块回退**：不支持工具调用的模型可输出 ` ```ai2ui ` 代码块，`packages/markdown` 识别后交给同一渲染器；流式中显示骨架，代码块闭合后校验渲染。
3. **使用指南按需注入**：系统提示只放一行能力说明；首次调用前由工具描述携带精简指南（何时用表格/图表/表单、何时别用 UI 直接回答文字），避免长期占用上下文。参考 WorkBuddy `widget_guidelines`。
4. **扩展**：`packages/engine/src/extension-ui/bridge.ts:178` 的 `setWidget` 增加 `ai2ui` 载荷，扩展可在输入框上方挂结构化卡片。
5. **A2A**：远端节点返回的 A2UI part 经同一校验器后渲染，来源标注对端节点名。

### 8.5 前端实现
| ID | 内容 | 位置 |
|---|---|---|

- 积分、邀请、升级类商业化入口：不进入主流程。
- 复杂图表交互（缩放、刷选、联动）。
