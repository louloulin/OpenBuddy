## §0 结论先行

**一句话**：WorkBuddy 的"应用"本质是**一个统一的插件包体系**（`.codebuddy-plugin` manifest + 分类注册 + 场景组合 + 会话内推荐），OpenBuddy 已有 Pi Package 这条同构的机制（`package.json#pi` + `DefaultPackageManager`）却没有把它**产品化成"应用"**。本计划做两件事：

1. **平台层**：在 OpenBuddy 上建"应用平台"——应用清单（manifest）、应用选择器 UI、场景（welcomeMode/interactionMode）体系、会话内应用推荐、上下文占用管理。全部落在 Pi 原语上，不造新运行时。
2. **应用层**：把 UpUp 接入为第一个第三方应用（投研助手），验证平台。

**关键判断（REA 证据支撑）**：

- WorkBuddy 的一切能力（场景、技能、专家、Office 工具、多模态、连接器）都注册在**同一个内置 marketplace**（`resources/plugins/workbuddy-builtin/.codebuddy-plugin/marketplace.json`），共 40 个包、6 类 category：`welcomeMode`×3、`interaction`×5、`template`×1、`skill`×22、`mcp-app`×1、`builtin-plugin`×8。**没有第二套插件系统**。
- 插件 manifest（`.codebuddy-plugin/plugin.json`）字段：`name/version/category/keywords` + 资源键 `agents[] / skills[] / commands / hooks / mcpServers / experts[] / workbuddy.dependencies[]`。与 Pi 的 `pi.extensions/skills/prompts` 清单**同构**，多出的部分（mcpServers/hooks）Pi 1.5.2 也有对应物（pi-mcp、extension 事件）。
- 会话内推荐闭环存在且由提示词驱动：`interactionmode/craft/fragments/plugin-recommendation.md` 要求模型用 `search_plugins` / `suggest_plugin_install` 工具弹出"连接器/专家"推荐卡（每次最多 3 个候选、单卡片渲染、禁止文本列表）。
- 截图中的"Buddy 应用"选择器（最近使用 + 推荐：通达信·证券智能投研交易助手、东方财富妙想·智能投研助理、MOSS 增长谋士、分贝通、Flova.ai）= **已安装应用的快捷入口 + 推荐位**；企点营销云页面的"经营与洞察/消费者运营/企微运营"标签 + 能力 chips = **应用自带场景 + 技能清单**；"3 项技能/插件/MCP 已 14 天未使用，一键关闭"= **上下文占用治理**。
- 金融能力在 WorkBuddy 里**不是硬编码**，而是一个内置技能包 `workbuddy-finance-skill`（45 个 references + 15 个 Python 脚本 + 检索路由表"金融 MCP → domain_search → WebSearch"+ 固定免责声明），数据靠用户已连接的金融类 MCP。**投资应用 = 技能包 + 连接器（MCP）的组合**，这正对应 UpUp 的 Pi Package 结构。

## §1 WorkBuddy 应用架构解剖（REA 证据）

### 1.1 包体系与分类

```
app.asar
├── main/                     主进程（模块化打包，含 window-apps、app-server-mcp-apps-host、plugin-types）
├── preload/                  contextBridge
├── renderer/                 React 渲染层（BuddyAppsPanel、colleagues-panel、skills-panel、SecurityCenterPanel…）
└── resources/plugins/workbuddy-builtin/
    ├── .codebuddy-plugin/marketplace.json   ← 统一内置市场清单（40 包）
    ├── welcomemode/{code,work,design}/      ← 根代理场景：agents/*.md + prompt.tpl（nunjucks）
    ├── interactionmode/{craft,ask,plan,expert,quick}/fragments/*.md   ← 交互模式片段
    ├── skills/<24 个技能>/SKILL.md + references/ + scripts/
    ├── mcps/{agently-cli,miora-mcp}/        ← 内置 MCP
    └── builtin-plugins/{docx,pptx,sheetagent,tencent-docs,…}/          ← Office/连接器插件
```

### 1.2 六类 category 与职责

| category | 数量 | 例子 | 本质 |
|---|---|---|---|
| `welcomeMode` | 3 | code / work / design | **首页根代理**：`settings.json` 只有一行 `{"agent":"work"}`；`agents/work.md` 是一行 include；`prompt.tpl`（304 行 nunjucks）按 `workMode` 变量拼装交互模式片段 |
| `interaction` | 5 | craft / ask / plan / expert / quick | **交互模式**：5 组 prompt 片段（interaction / current-mode / agent-loop / tool-use / result-presentation），由 welcomeMode 模板 include |
| `skill` | 22 | finance-skill / expert-manager / recommend-connectors / library / sites / cloud-service | SKILL.md + references + scripts 的知识包 |
| `mcp-app` | 1 | mcp-miora | 内置 MCP 服务 |
| `builtin-plugin` | 8 | docx / pptx / sheetagent / tencent-docs | agents + skills + hooks + mcpServers 的复合插件（如 sheetagent：`commands` + `skills` + `hooks/hooks.json` + `mcpServers:{command,args,env,defer_loading}`） |
| `template` | 1 | prompt-common | 共享模板片段 |

### 1.3 四个产品机制（截图 ↔ 代码对应）

1. **Buddy 应用选择器**（侧栏放大镜/Buddy 应用 → 最近使用 + 推荐卡片）。每个应用=插件包，带 icon、一句话定位（"证券智能投研交易助手"）。主进程对应 `main/window-apps.js`、`main/app-server-mcp-apps-host.js`；渲染层 `renderer/assets/BuddyAppsPanel-*.js`。
2. **应用内场景**：企点营销云打开后是"经营与洞察 / 消费者运营 / 企微运营"三个 tab + 能力 chips + 示例 prompt 输入框。对应 `scenes.json` 结构：`{id, name, icon, mode, promptTitles[], prompts[]}`（design 场景文件已解包验证）。
3. **会话内推荐**：任务缺外部能力时，模型调 `search_plugins(type=connector|expert, userIntent)` → `suggest_plugin_install(pluginId1..3)` 渲染**单张推荐卡**；`recommend-connectors` / `recommend-experts` 两个技能承载该流程；规则：禁止编 ID、禁止文本列表、已绑定不推、每响应只调一次。
4. **上下文占用治理**：宿主统计技能/插件/MCP 的最近使用时间，≥14 天未用就弹卡建议"一键关闭/不再提醒"。对应提示词里的"已启用的技能、插件和 MCP 会向模型提供说明并占用上下文"。

### 1.4 专家包（expert-manager 技能定义的规范）

- 两种类型：`expertType: agent | team`；展示字段固定：`profession` / `displayName` / `categoryId` / `displayDescription`(40–50 字) / `tags`(固定 3) / `quickPrompts`(固定 3，第一条兼作 defaultInitPrompt)。
- 生命周期脚本化：init → 生成 → 头像 → validate → register → package；安装位置固定在 `$WORKBUDDY_CONFIG_DIR/plugins/marketplaces/my-experts/plugins`（用户专家）。
- OpenBuddy 对应物已存在：`experts` 模块（W2.1–W2.3）+ `ExpertStore` 的目录体系。差距是**包格式规范**与**校验/打包脚本**。

## §2 OpenBuddy 现状 ↔ WorkBuddy 差距映射

| WorkBuddy 机制 | OpenBuddy 现状 | 差距 |
|---|---|---|
| 统一 marketplace manifest（6 类 category） | Pi `package.json#pi`（extensions/skills/prompts/themes 4 键）+ `settings#packages` | 无分类/无推荐/无启用治理；manifest 语义未产品化 |
| Buddy 应用选择器 | FeatureRegistry（`registry.ts`）+ `host_capabilities` 显隐 | 是"功能开关"不是"应用"概念；无第三方应用入口 |
| 场景体系（welcomeMode/interactionMode + scenes.json） | 首页 HomePage 无场景；专家人设（persona builtin） | 无根代理场景、无场景卡数据结构 |
| 会话内推荐（search_plugins / suggest_plugin_install 卡片） | 无 | 无推荐工具与卡片 UI |
| 上下文占用治理（14 天未用提醒/一键关闭） | 技能/MCP/扩展可开关但无使用统计 | 无 usage 跟踪与提醒 |
| 插件安装/市场 | `PluginsPanel`/`MarketplacePanel` UI 已有，后端 `plugins_list`/`marketplace_*` 延迟命令未实现 | Pi `DefaultPackageManager` 完全未接入（`session-pool.ts:53` 用 `noExtensions` 全关） |
| 专家包规范 + 校验脚本 | experts 模块可读写 | 无 schema 校验、无打包/导入 |
| 投研应用 | 无 | UpUp 可整包接入（同为 Pi 1.5.2） |

## §3 目标架构：OpenBuddy 应用平台

### 3.1 概念模型（映射到 Pi 原语）

```
Buddy 应用 (App)
  = 一个 Pi Package（git/npm/本地），manifest 含分类与展示元数据
  = 应用卡（icon/名称/一句话/分类/状态） + 资源（extensions 工具 / skills / prompts）
  + 可选：应用场景 scenes.json（打开应用 = 新会话 + 根代理 prompt + 推荐 prompt）
  + 可选：绑定的 MCP 连接器

平台层（OpenBuddy 主进程）
  AppRegistry      ← DefaultPackageManager.listConfiguredPackages() + 应用 manifest 解析
  AppPicker UI     ← 侧栏"应用"入口：最近使用 + 全部 + 添加
  SessionComposer  ← 应用/场景选中 → 会话的 appendSystemPrompt + 推荐技能注入（复用 persona builtin 通道）
  UsageTracker     ← 记录工具调用/技能触发时间 → 14 天未用提醒（复用 notification 通道）
  RecommendLoop    ← 内置扩展注册 ob_app_search / ob_app_recommend 工具 → 渲染层推荐卡（复用 agent://ui 通道）
```

### 3.2 应用 manifest（OpenBuddy 约定，向前兼容 Pi）

Pi 原生读 4 键之外，OpenBuddy 增读 `pi.app`（可选，缺省则不是"应用"只是普通包）：

```jsonc
{
  "name": "@upup/investment-app",
  "pi": {
    "extensions": ["./extensions"], "skills": ["./skills"], "prompts": ["./prompts"],
    "app": {
      "kind": "app",                       // app | connector | skill-pack（对齐 WorkBuddy 三类）
      "icon": "./assets/icon.png",
      "tagline": "证券智能投研助手",
      "category": "finance",               // 平台分类
      "scenes": "./scenes.json",           // 可选：场景卡
      "mcp": "./.mcp.json"                 // 可选：随应用注册的 MCP
    }
  }
}
```

### 3.3 UpUp 作为投研应用的接入方式（三选一，推荐 A）

| 方案 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A. Pi Package 整包（推荐）** | `pkg_install git:https://github.com/louloulin/upup`；Pi 读其根 `package.json#pi.extensions`（指向 `packages/pi-app/src/pi-plugin-extension.ts`），jiti 现场转译，全部 `@upup/pi-*` 扩展（275 工具、32 技能、workflows/policies）挂进会话 | 一次安装全量能力；skills/prompts 原生生效；UpUp 文档已验证该路径（`pi install <repo>`）；MIT 许可 | 包大；需按其文档处理 npm 三教训（legacy-peer-deps / 无 workspace: / node export condition）；会话启动变慢 → 需要按需启用子包 |
| B. MCP 桥 | `upup --stdio`（JSON-RPC）作为 MCP server 注册 | 进程隔离、松耦合 | 丢 skills/prompts/workflows（MCP 只有工具）；双运行时开销 |
| C. 源码移植 | 把 `pi-market-data`/`pi-technical`/`pi-investment-analysis`/`pi-risk` 的 TS 移植进 `packages/services/src/market/` 做内置扩展 | 可控、精简 | 放弃 UpUp 生态更新；工作量大；违背"应用平台"定位 |

**决策：A 为主，B 作为 A 失败时的兜底**；不做 C（平台定位下，内置代码只做平台原语，领域能力一律走应用）。

### 3.4 UpUp 接入的裁剪（重要）

整包含 43 包，不应全量默认启用。利用 UpUp 自身的包开关（`resolveUpupExtensionPaths()` 尊重用户 toggle）与 OpenBuddy 的 manifest `pi.app`，首版**只启用投研核心子集**：

```
启用：pi-market-data(24 工具) · pi-technical(9) · pi-investment-analysis(16) · pi-risk(16)
      pi-investment-workflow(2, /invest 五阶段) · memory(12, 投研记忆)
暂缓：pi-portfolio(28) · pi-finance-sdk(44, 含 place_trade_order——平台红线：不接入真实交易)
      pi-notify / gateway / daemon / cron（自动化走 OpenBuddy 自己的 automation 地基）
```

安全对齐：UpUp 的 fail-closed 五件套（`place_trade_order` 等）与 OpenBuddy 权限门并存——所有 UpUp 工具照常过 `tool_call` 审批；只读行情/估值类在服务里登记进 `READ_ONLY` 白名单（`permissions.ts:31`）。
