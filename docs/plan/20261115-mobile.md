## §0 结论先行

1. **网关移植 = 复制 + 命名清理，零逻辑改动**（✅ 已完成，`bun test` **359 pass / 0 fail**，新增 expo 推送 5 测）。
2. **协议对接的核心设计不变**：桌面新增 Pi Bridge Server，把 OpenBuddy IPC 契约原样映射为 HTTP + SSE（并已实现 WS 多路复用），网关原封不动隧道转发——**网关零逻辑改动**。
3. **手机端选型从 Capacitor 改为 Expo**，原因是"手机端是功能子集"这一产品事实：
   - `apps/web` 有 **210 个 tsx、6.0MB src**，全部是 React DOM 组件；把桌面 UI 塞进 WebView 需要改造 210 个组件的响应式，产物仍是 WebView 手感。
   - 而能力层是**纯 TS、零 DOM**：`packages/protocol`、`packages/chat-core`（21 文件，无 `window/document/react`）、`packages/client/src/api/*`（仅耦合 `ipc.ts`）、`GatewayTransport` —— **全部可复用**。
   - 结论：**只重写"像素层"（20–30 个组件），复用"能力层"（~100%）**，这是 Expo 路线的真实成本模型。
4. **H5 不废弃**：网关 `/h5` 继续托管 `apps/web` 构建产物，作为零安装、全功能、平板/浏览器可用的兜底形态。两种形态共用同一 Transport 契约。

## §1 竞品分析与产品定义

### 1.1 功能切分（手机 vs 桌面）

> Kimi、豆包按公开产品形态归纳；Grok bot / Muse 按交互范式提炼原则；WorkBuddy 依据本机逆向资料（`/Users/louloulin/lumosaiup/docs/architecture/workbuddy-*.md`）。

| 产品 | 桌面端定位与能力 | 手机端定位与能力 | 手机独有 | 桌面独有 |
|---|---|---|---|---|
| **Kimi** | 长文/多文件深度处理：超长上下文、批量上传、Kimi+ 智能体、插件、划词、代码表格 | 碎片时间随身问答：对话、语音输入/通话、拍照识题、联网搜索、受限文件、通知 | 语音通话、相机、系统分享、推送、离线缓存 | 多文件工作流、浏览器插件、划词、批量输出 |
| **豆包** | 生产力工具：写作、长文、文件、插件、划词、屏幕/会议辅助、编程 | **语音优先的随身助手**：实时语音通话、拍照、AI 搜索、智能体广场、图像/音乐生成、悬浮球 | 实时语音、悬浮球、系统分享、相机 | 文件批处理、屏幕理解、插件体系、编程 |
| **Grok bot** | 深度问答 + 实时信息 | **实时多模态对话**：低延迟语音、可打断、相机视觉、实时搜索、人格化 | 实时语音、视觉、人格模式 | 长文与复杂任务 |
| **Muse** | 个人知识/记忆工作台 | **记忆优先的安静伴侣**：回顾、联想、离线可用的个人资料 | 生物识别、离线记忆、情感化提醒 | 批量整理与编辑 |
| **WorkBuddy** | **执行主机**：agent 执行、工具/connector、OAuth、计费、RBAC、本地文件、MCP | **远程遥控器 + 审批终端**：会话、对话、审批、推送、扫码配对 | 推送审批、扫码配对 | MCP/connector/计费/RBAC/文件写 |

### 1.2 四条产品规律

1. **手机端是"高频链路最短化"，不是功能镜像**：会话 → 输入（语音/拍照）→ 流式回复 → 审批 → 通知回跳。
2. **手机独有能力必须专门设计**：语音、相机、系统分享、推送深链、安全存储、离线缓存。
3. **桌面保留重资产**：文件系统写、MCP/扩展管理、批量任务、密钥、计费与管理面。
4. **两端共享"状态与契约"，不共享"像素"**——这也是三家都没有把桌面 UI 硬塞进手机的原因。

### 1.3 OpenBuddy Mobile 定位

> **桌面 Pi 的随身遥控器 + 语音/视觉入口 + 审批终端。**
> 手机不执行工具、不持有 LLM key、不写桌面文件系统；它负责"开口、看一眼、拍一下、点一下批准"。

**五条核心链路（P0）**

1. **扫码配对**：10 秒内完成，device token 存 SecureStore。
2. **会话列表**：缓存优先渲染（<300ms 可见），下拉刷新。
3. **聊天**：文本 / 语音 / 拍照 → 流式回复，支持中止、队列、分支入口。
4. **审批**：推送到达 → 打开审批卡 → 一键批准/拒绝（`approve` scope）。
5. **通知深链**：点开直达会话与对应消息位置。

**差异化（学习 Grok bot / Muse）**

| 方向 | 设计 |
|---|---|
| **私有** | LLM key 永不出桌面；手机只是镜头与麦克风（对齐 WorkBuddy "遥控器"模型） |
| **语音优先**（Grok bot） | 流式 ASR → `agent_send` → 流式回复 + TTS 朗读；v2 做实时双向语音 |
| **视觉入口**（Grok bot / 豆包） | 相机拍照 → 端侧压缩 → 上传桌面 → 视觉模型理解 |
| **记忆**（Muse） | 复用 `memory_*` 命令：跨会话召回、资料库浏览、信任门可见 |
| **人格**（Grok bot / 豆包智能体） | 复用 `experts_*`：专家即"人格切换"，手机端只读+选择 |
| **克制**（Muse） | 默认无噪音：只有审批/完成/被提问才推送；深色优先、安静动效 |


### 1.4 与千问、Kimi 的功能差距（2026-11 实测 App Store 描述 + 官网）

> 依据：`千问 - 阿里AI助手` 与 `Kimi` 的 App Store 应用描述，以及 kimi.com 首页导航。
> 两家都是"云端大模型 App"，能力远多于我们；但**只有与"遥控电脑 agent"这一形态直接相关的部分才是我们的差距**，其余（3D 建模、视频生成、点外卖、政务代办）属于云端产品形态，不在 OpenBuddy 手机端的职责内。

**Kimi 里与我们同源的能力**：官方写明"**远程控制**：随时随地，你都可以通过手机控制电脑上的 Kimi Work。尚未完成的任务，都可以在手机上接着做"、"多端同步：手机、电脑、网页无缝衔接，对话、文件与工作进度实时同步"。

**两家共同具备、且我们缺的**

| 能力 | 千问 | Kimi | OpenBuddy 现状 | 处置 |

**明确不追的（形态不同，追踪它们只会稀释产品）**：3D 建模与游戏生成（Kimi）、视频生成（Wan 3.0，千问）、AI PPT 模板、点外卖/订酒店/政务代办、股票金融插件、小讲堂与作业批改。理由：这些能力的前提是**云端算力与云端账户**，而 OpenBuddy 手机端的承诺是"你的电脑，你的会话，你的密钥"。把它们搬过来等于否定位。

**由此确立的一条产品原则**：手机端只补"**遥控器该有的旋钮**"——看得见电脑的状态、能改电脑的行为、能在电脑上继续未完成的工作；不复制云端 App 的内容生态。

### 3.2 传输层：SSE（已上线）+ WS 多路复用（v1 优化）

| 场景 | 通道 | 状态 |
|---|---|---|
| Expo 原生 App（经网关） | `expo/fetch` + `GET /events?since=seq`（SSE）+ `POST /cmd/:cmd` | ✅ 已实现并通过真栈验证 |
| H5 / 浏览器 | 同一 SSE + POST 契约（`GatewayTransport`） | ✅ 同一实现 |
| 直连 / 局域网 / P2P | WS 多路复用 `openbuddy/bridge/1`（`GET /ws`） | ✅ 服务端 + `WsBridgeTransport` 已实现，5 个真栈用例 |

**为什么 SSE 仍是经网关的默认**：Expo SDK 58 的 `expo/fetch` 可流式读取 `Response.body`，
`GatewayTransport` 在原生端可用；Hermes 缺少 `TextDecoderStream`，传输层已加手动解码回退（有单测）。
WS 多路复用已实现（更省电、可 ping），但网关目前只桥接 `/ws/:sessionId` 到桌面的同名路径，
把 `/api/ws` 纳入网关隧道属于后续网关侧的增量路由；直连（LAN/P2P）已可直接使用 WS。

**WS 帧格式（`openbuddy/bridge/1`，已实现）**

```jsonc
{ "t": "cmd",   "id": "a1", "command": "agent_send", "payload": { } }   // 手机→桌面
{ "t": "reply", "id": "a1", "ok": true, "result": { } }                 // 桌面→手机
{ "t": "evt",   "event": "agent://event", "seq": 1041, "payload": { } } // 桌面→手机（seq 单调）
{ "t": "ping" }                                                          // 30s；弱网 15s
```

- **seq 与重放**：PiBridge 已有 EventBuffer（2048）；重连带 `since` 补发，缺口过大发 `resync`。
- **压缩**：沿用 `agentCore` 语义，WS 帧 JSON gzip（事件流帧除外），16MB 上限直传。

### 3.3 包边界

```
新增：packages/gateway（Bun，独立 bun.lock）· packages/pi-bridge · apps/mobile（Expo）
复用：protocol · chat-core · client（api + GatewayTransport）· host/engine（桌面侧）
H5：apps/web（仅网关 /h5 托管，不参与原生构建）
```

约束：
- `client`：`GatewayTransport` 仅用 Web 标准 API（fetch/WebSocket/TextDecoder），不引 Node/Electron。
- `pi-bridge`：允许依赖 host/engine/protocol；禁止依赖 electron（便于迁 utilityProcess）。
- `apps/mobile`：只依赖 `protocol` / `chat-core` / `client`（不得引 `ui` / `markdown` / `apps/web`）。
- `gateway`：允许 `hono` + Bun 内置；禁止依赖 `@openbuddy/*`。

- 输入卡圆角 24px、聚焦时边框变成 `--ob-focus`，与 `.wb-composer:focus-within` 一字不差。

> 思考块、工具卡与完整回复都出现在 DOM 中。

### 4.3.1 核心链路时序（发一条语音消息）

```
手机                        GatewayTransport           网关隧道          PiBridge           PiEngine
按住说话 ── ASR ──► invoke('agent_send',{text}) ──► /api/cmd ──► validate+handler ──► session
                                                                    │
听 TTS ◄── evt(agent_settled) ◄── SSE/WS evt ◄──────────────────────┘ 流式 SessionUpdate*
```

### 4.6 缓存与离线

- **首屏**：SQLite 读最近会话 + 最近 N 条消息 → 立即渲染 → Transport `open` 后增量同步（`agent_load_session`）。
- **断线**：指数退避（1s→2s→5s→15s），重连后按 `seq` 补齐；缺口过大走 `resync` + 快照。
- **队列**：离线时发送进入本地 outbox，`state === "open"` 后按序重发（幂等靠客户端 promptId）。
- **媒体**：图片只在发送时上传，不落本地相册。

### 5.3 与共享层对接

```ts
// apps/mobile/src/transport/index.ts
import { GatewayTransport } from "@openbuddy/client/gateway-transport";

export const transport = new GatewayTransport({
  baseUrl: `${gatewayUrl}/api`,   // 网关隧道保留前缀
  token: deviceToken,             // SecureStore 读取
  // Expo: 用 expo/fetch（支持流式）或切换到 WS 通道
});
```

- **Transport 注入点**：手机端不经过 `ipc.ts`（那是 Electron preload）；`src/transport/index.ts` 直接构造
  `GatewayTransport`，并注入 `expo/fetch`（原生可流式读取 `Response.body`）。
- **共享层复用边界（实测结论）**：`protocol` / `chat-core` / `client` 的 `transport` 与 `gateway-transport`
  全部直接复用；`packages/client/src/api/*` 仍绑定 `ipc.ts`，因此**手机端不复用 api 包装层**，而是在
  `apps/mobile/src/core/*` 中按需直接 `invoke`。这样既不需要改 18 个域文件，也不会把 preload 依赖带进原生包。
  - 若将来 H5 也要复用 api 包装层，再在 `ipc.ts` 内做运行时分流（`window.openbuddy` → Electron；否则 → Transport 单例）。
- **错误语义**：`not_implemented` / 未在 capabilities 中 → 统一提示"此功能需在桌面操作"
  （`apps/mobile/src/core/surface.ts:unavailableReason`，与 FeatureRegistry 隐藏逻辑一致）。

### 5.4 流式渲染性能

- 事件经 `applyUpdate` 增量折叠；只有「流式那一行」被替换，其余行引用不变，配合 `memo` 的
  `MessageRow` 让列表不整体重渲染。
- 工具卡按 `toolcall_start → toolcall_delta → toolcall_end` 原地更新（不新增行）。
- Markdown 增量解析：只重解析最后一个未闭合块；已完成块缓存 AST（v1 先做纯文本 + 代码等宽，富文本在后续增强）。
- 图片/工具卡懒加载；`FlashList` v2 自适应高度（v2 已移除 `estimatedItemSize`）。

### 5.5 Markdown / 代码高亮

- `lowlight` 是纯 JS（输出 hast），**不依赖 DOM**，可在 RN 中遍历 hast → `<Text>` span。
- 代码块：等宽字体 + 横向滚动 + 一键复制；v1 先不做行号。
- 表格/KaTeX：v1 降级为纯文本表格；公式后续用 WebView 小组件按需渲染。

### 5.6 相机与附件上传协议（关键设计缺口）

现状：`validate.ts` 明确禁止 `agent_send` 携带 `images`（渲染层图片字节），只允许 `attachments: [{ path }]`。手机拿不到桌面路径，因此需要一条上传通道：

```
1. 手机拍照 → expo-image-manipulator 压缩（长边 ≤1600，JPEG 质量 0.8，目标 <1MB）
2. POST {gateway}/api/upload
     headers: authorization: Bearer <deviceToken>, content-type: image/jpeg
     body: 图片字节
   → 网关隧道 → PiBridge 写入桌面临时目录
   → 200 { path: "/tmp/openbuddy-upload/<uuid>.jpg" }
3. agent_send { text, attachments: [{ path }] }
```

实现要点：
- 网关 `GATEWAY_MAX_BODY_BYTES` 默认 20MB，足够单图；多图逐张上传。
- PiBridge 校验 `content-type` 白名单（image/jpeg|png|webp）、大小上限、文件名随机化，禁止路径穿越。
- 临时目录按会话/日期隔离，启动时清理 24h 前文件。
- 该接口同样受 Bearer 鉴权与 scope（`sessions:write`）约束。

### 5.7 语音

| 版本 | 方案 |
|---|---|
| v1 | 端侧流式 ASR（`expo-speech-recognition`）→ 文本 `agent_send`；回复用 `expo-speech` 播报 |
| v2 | 实时双向语音：手机采集 PCM → 网关/桌面 STT → PiEngine → TTS 流回（对齐 Grok bot 的可打断体验） |

### 5.8 推送

- 手机 `expo-notifications` 获取推送 token，随设备注册上报。
- 网关现有 `fcm` provider 可直连 FCM（Android）；iOS 走 APNs。
- **已新增 `expo` provider**（`packages/gateway/src/push/expo.ts`）：POST `https://exp.host/--/api/v2/push/send`，无需 APNs 证书；`DeviceNotRegistered`/4xx 判永久失败，5xx 可重试，5 个单测。可选 `GATEWAY_EXPO_ACCESS_TOKEN` 提升配额。
- 通知负载携带 `sessionId` + `kind`，点击深链 `openbuddy://session/<id>?request=<requestId>`。

**闭环链路（已实测）**

```
桌面引擎事件 ──► PiBridge GET /api/sessions/live-status ──► 网关 watcher（每 pushWatchIntervalMs 轮询）
      ──► push dispatcher（fcm / webhook / expo）──► 手机
```

`live-status` 是由桥**从同一条事件流**归纳出来的（不读引擎内部）：`agent://permission` → waiting（带 requestId）、`agent_settled` → 移除、运行中静默 10 分钟 → 移除（防止崩溃的桌面永远显示"还在跑"）。这条链路此前是断的——网关只会拿到 404，任何推送都不会发出。

### 5.9 安全

- device token 存 Keychain/Keystore（`expo-secure-store`），不进 AsyncStorage。
- 启动可开生物识别锁；后台切换 30s 后要求重新解锁。
- 生产强制 `GATEWAY_REQUIRE_TLS`；开发允许局域网明文但显式提示。
- 吊销设备即时断连（网关 `trackDeviceSocket` 原版语义），App 收到 401 清 token 回配对页。

## §8 风险与对策

| 风险 | 对策 |
|---|---|
| **两套 UI 长期维护**（Expo + H5） | H5 定位为"只读兜底"，新功能优先原生；共享层（协议/chat-core/api）保证行为一致 |
| RN 全局 fetch 不支持流式 SSE | 已用 `expo/fetch` + Hermes 手动解码解决（有单测）；WS 多路复用（Phase 2.4）作为省电优化，不阻塞 |
| RN Markdown/高亮不完整 | `lowlight` DOM-free + 自定义 renderer；表格/公式先降级 |
| 相机附件与 `validate` 冲突 | 独立 `/api/upload` 落盘 + `attachments.path`，不破坏现有契约 |
| Expo 推送需要 dev build | EAS dev client；iOS 需 APNs/Expo 账号 |
| 桌面 PiBridge 与主进程同命 | v1 主进程内跑；v2 迁 utilityProcess |
| 手机端 api 层仍耦合 `ipc.ts` | 在 `ipc.ts` 内做运行时分流（单点改造） |
| 网关与 pnpm 依赖图共存 | gateway 独立 bun.lock 与 CI job |
| 设备丢失 | SecureStore + 生物识别 + 即时吊销 + 强制 TLS |

## 附录 E — 如何运行手机端

```bash
pnpm install
# 纯逻辑层单测（无需模拟器）
npx vitest run apps/mobile

# 全链路验证（无 LLM key）
bun run scripts/e2e-mobile.ts        # 协议桥
bun run scripts/e2e-mobile-app.ts    # App 逻辑层
bun run scripts/e2e-mobile-push.ts   # 推送闭环（desktop → gateway → device）
bun run scripts/e2e-mobile-h5.ts     # 浏览器兜底（先 npx vite build）
node  scripts/run-desktop-bridge-e2e.mjs   # 真实桌面桥（Bun 网关 + Node 桌面）

# 启动 App（需 EAS dev build 才能用相机）
cd apps/mobile && npx expo start

# 打包校验
cd apps/mobile && npx expo export --platform ios --platform android
```

**桌面侧环境变量（启用手机接入）**

| 变量 | 作用 |
|---|---|
| `OPENBUDDY_GATEWAY_URL` | 网关地址；不设则完全不开端口 |
| `OPENBUDDY_GATEWAY_AGENT_TOKEN` | 桌面 WS 隧道凭据 |
| `OPENBUDDY_GATEWAY_ADMIN_TOKEN` | 设置页生成配对码 / 列设备 / 吊销用；只在主进程 |
| `OPENBUDDY_GATEWAY_DESKTOP_ID` | 可选：把配对码绑定到某台桌面 |
