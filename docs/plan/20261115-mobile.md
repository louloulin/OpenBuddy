## §0 结论先行

1. **网关移植 = 复制 + 命名清理，零逻辑改动**。lumos gateway 对外仅依赖 `hono ^4.13`，已复制到 `packages/gateway/`，`bun test` **354 pass / 0 fail**。
2. **手机端方案 = Capacitor 壳 + `apps/web` 产物**（v0 先纯 H5 挂网关 `/h5`）。UI 复用 ~100%；本仓库已具备全部前置条件：
   - `packages/client/src/transport.ts` 已有 `Transport` 接口 + `ElectronTransport`/`MemoryTransport`，注释明确"**WsTransport follows in P4 against the same contract**"——手机端正是它的落地场景。
   - `apps/web` 的 FeatureRegistry（`registry.ts`）已有 `platforms: ("desktop"|"web")[]` 过滤与 `host_capabilities` 能力探测（`capabilities-store.ts`），桌面专属功能自动隐藏，**UI 层零改动适配手机**。
3. **协议对接的核心设计（本计划最重要决策）**：lumos 网关的隧道原语是"HTTP 转发 + WS 隧道"（`/api/*`/`/proxy/*`/`/ws/:sessionId`），而 OpenBuddy 的线协议是 **IPC 命令/事件**（`packages/protocol`：`COMMANDS` 白名单 100+ 命令、`EVENTS` 26 个事件、`SessionUpdate` DTO 带增量流）。对接方案：**桌面新增 Pi Bridge Server，把 IPC 契约原样映射到 HTTP+SSE**，网关原封不动地隧道转发——网关零改动，协议复用率 100%（详见 §3）。
4. **性能瓶颈在流式链路，不在 UI**：网关 SSE 零缓冲直通 + WS 隧道 gzip（SSE 除外）lumos 已做对；手机侧要点是单 WS 复用连接（省电）、本地缓存先渲染、rAF 批量渲染。

| 维度 | lumos 手机协议 | OpenBuddy 协议 | 对策 |
|---|---|---|---|

## §3 协议桥设计（核心）

### 3.1 `packages/pi-bridge`（新增）

职责：把 OpenBuddy IPC 契约（COMMANDS/EVENTS）映射为网关可隧道转发的 HTTP/WS，与 `apps/desktop/src/ipc/register.ts` 走**同一批 host handlers**。

```
pi-bridge/
  server.ts        Hono app（Bun 或 Electron utilityProcess 内跑）
                   POST /cmd/:command   → validateCommandPayload → handlers[command](payload)
                   GET  /events         → SSE（心跳 25s； Last-Event-ID = seq 重放）
                   GET  /ws             → 升级为复用通道（推荐，见 3.2）
                   GET  /health         → readiness
  frames.ts        WS 复用帧协议（openbuddy/bridge/1）
  agent-link.ts    包装 gateway/src/agentCore.createAgentClient()（从 lumos 提炼为共享模块）
  caps.ts          host_capabilities 应答：platform:"mobile-host"，声明手机可用命令/事件子集
```

**命令子集（手机端 `host_capabilities` 应答）**：
- 保留：`agent_*`（会话/发送/取消/分支/检查点/回退）、`providers_list`（只读）、`experts_*`、`memory_*`、`session_search`、`notification_*`、`tasks_list`、`plan` 相关
- 排除：`window_*`、`dialog_*`、`clipboard_*`（native 桌面能力）、`mcp_config_*`（管理面）、文件系统写类命令（v1 只读浏览）
- FeatureRegistry 的 `platforms`/`requires` 机制自动隐藏被排除功能——**web UI 零改动**。

### 3.2 WS 复用帧协议 `openbuddy/bridge/1`（v1）

lumos 的 `/ws/:sessionId` 是每会话一连接；OpenBuddy 事件是全局总线。手机上每会话一连接浪费（移动网络握手贵、耗电），设计为**单连接多路复用**：

```jsonc
// 帧 = { t: "cmd"|"reply"|"evt"|"ping"|"sub"|"unsub", id?, command?, payload?, seq? }
{ t:"cmd",   id:"a1", command:"agent_send", payload:{…} }        // 手机→桌面
{ t:"reply", id:"a1", ok:true, result:{…} }                      // 桌面→手机
{ t:"evt",   event:"agent://event", seq:1041,
  payload:{ sessionId, event:SessionUpdate } }                   // 桌面→手机，seq 单调
{ t:"ping" }                                                     // 30s；弱网自动 15s
```

- **seq 持久化**：PiBridge 把每条事件 seq 写内存环形缓冲（≥2048 条）；手机重连带 `Last-Event-ID: seq`，桌面补发缺口，缺口过大则发 `resync` 提示客户端拉快照（`agent_load_session`）。
- **SSE 回退**：老网关/纯 HTTP 场景走 `GET /events`（SSE）+ `POST /cmd/:command`，同一套帧语义拆到两条通道。v1 默认 WS。
- **压缩**：沿用 `agentCore.compressibleResponse` 语义——WS 帧内 JSON gzip（排除事件流帧），16MB 上限转直传。

### 3.3 与网关的对接点（网关零改动）

| 网关原语 | PiBridge 用法 |
|---|---|
| `POST /relay/agent`（WS） | agent-link 接入，present agent token |
| `AgentHub.openWs(desktopId, path, …)` | 手机 `/relay/device` 的 WS 帧被隧道到桌面的 `/ws`（帧协议透传，网关不理解内容——**正因如此网关零改动**） |
| `app.all /api/*` → `forwardHttp` | SSE 回退通道 + providers_list 等纯请求型命令 |
| scope 映射 | WS 帧内命令按 GET/写语义检查 sessions:read/write；`approve` scope 对应 `agent_resolve_permission` |
| `DeviceRoute` 钉定 | 配对即绑定 desktopId，桌面离线报 4503 不 fallback（原版语义保留） |

### 4.2 GatewayTransport（`packages/client`，新增 ~300 行）

```ts
export class GatewayTransport implements Transport {
  // invoke: WS 帧 {t:"cmd"} + promise map；WS 断开时排队重发或直接 reject(state==="closed")
  // listen: 本地 fan-out（对照 MemoryTransport 的 listeners 结构）；事件按 seq 去重排序
  // state/onState: WS readyState + 心跳超时判定 → connecting/open/closed
  // 配置: { gatewayUrl, deviceToken, installationId }（配对结果持久化于 Capacitor Preferences / localStorage）
}
```

要点：
- **事件缓冲与重放**：`listen` 挂上之前到达的事件按 seq 缓存，避免 `subscribeAgentEvents` 的 wire 竞态（对照 `api/events.ts` 现有订阅时序）。
- **断线策略**：指数退避（1s→2s→5s→15s 上限）+ 网络状态监听（Capacitor Network 插件）即时重连；重连成功后 `state()→open` 触发上层重新 `agent_load_session` + 按 seq 补齐（`transport.ts` 注释中既定的 reconnect 语义）。
- **请求超时**：长命令（`agent_send`）无超时靠事件流推进；普通命令 30s 超时。

## §5 性能设计

### 5.1 网关（Bun，保持原版即为最优）

| 项 | 现状（保留） | 指标 |
|---|---|---|
| SSE 直通 | `accept-encoding: identity`，零缓冲 | TTFB = 桌面出 token 时间 + 1 跳 RTT |
| WS 隧道 | JSON gzip（SSE 排除）、16MB 流式上限 | 500KB 历史 → ~80KB 线上（lumos 实测注释） |
| sqlite | WAL（原版已开） | 审计异步批量写（核查点：确认 audit 不在请求路径同步写） |
| 限流 | device + IP 双桶，认证后才计费 | 原版保留 |
| 单文件分发 | `bun build --compile` → `openbuddy-gateway` | 冷启动 <100ms |

### 5.2 手机

| 项 | 设计 | 目标 |
|---|---|---|
| 冷启动 | 缓存优先渲染 + WebView 预热（v1） | <2s 首屏可交互 |
| 连接 | 单 WS 复用（§3.2），心跳自适应 30s/15s | 待机耗电最小化 |
| 流式渲染 | rAF 合帧；markdown 增量段渲染（复用现有 markdown host） | 60fps 打字机 |
| 重连 | Last-Event-ID 补发 + 快照兜底 | <3s 恢复，不丢 token |
| 包体 | apps/web 产物（共享 chunk 已拆） | 壳 +5MB |

## §7 风险与对策

| 风险 | 对策 |
|---|---|
| bun 与 pnpm 依赖图共存 | gateway 独立 bun.lock、独立 CI job，不进 workspace node_modules |
| WS 复用帧是自定义协议，网关透传但不理解 | 帧内自带 seq/id 自描述；SSE 回退通道保底；协议版本号 `openbuddy/bridge/1` |
| 手机端 api 层切 Transport 触碰 18 个域文件 | 按文件逐个迁移 + 现有 vi.mock 测试改注入，每步 CI 绿；先迁 session/turn（聊天主链路） |
| 桌面 PiBridge 与 Electron 主进程崩溃耦合 | v1 主进程内跑（与引擎同命）；v2 迁 utilityProcess（对齐 P2P 计划的隔离原则） |
| WebView 长列表/重 markdown 掉帧 | 虚拟化 + 增量渲染核查点；不达标再引入 预渲染层 |
| 移动端安全：设备丢失 | device token 存 Keychain/Keystore（Capacitor SecureStorage）；吊销即时生效；SSE/WS 强制 WSS（GATEWAY_REQUIRE_TLS） |
| 与 P2P 计划冲突 | §2.1 已画明双通道；网关 = 公网兜底，P2P = 直连优选，同一 PiBridge 上游 |
