## §0 结论先行

**一句话**：UpUp 是一个**自带 24 个子包白名单的 Pi 插件**——`pi install <upup>` 后，Pi 只加载一个 dispatcher（`packages/pi-app/src/pi-plugin-extension.ts`），由它按「env 路径 > 项目设置 > 内置白名单」解析出子包，再把工具/技能/prompt 挂进会话。所以 OpenBuddy 侧**不写安装器、不写适配层**，要做的是四件事：**装、指对 agentDir、按官方开关裁剪、把交易类工具 deny 掉**。

**六个判断（全部有代码依据）**

1. **加载入口唯一**：根 `package.json#pi.extensions` 指向 dispatcher；dispatcher 再动态 import 子包。Pi 侧只需要能加载这一个 TS 文件（jiti 转译）。
2. **子包来源三层**：`resolveConfiguredPiPackages(cwd)` → ① env `UPUP_PI_PACKAGE_PATHS`（必须同时给 `UPUP_PI_TRUSTED_PATHS`）② 项目 `.upup/settings.json` / `.pi/settings.json`（要求 `upupPiPackages.trustedPaths` + `pinnedPackages`，且**只允许项目内本地路径**）③ 内置白名单 `BUILTIN_PI_PACKAGES`（24 个包）。
3. **裁剪有官方开关**：`<agentDir>/settings.json` 里的 `upupPlugins: { enabled?, disabled? }`，由 `filterBuiltinCandidatesByToggles` 应用到内置白名单；键规范化为 `@upup/<目录>`。只有 `UPUP_BUILTIN_PLUGIN_DIRECTORIES`（22 项）可关，纯基础设施包设计上不可关。
4. **agentDir 决定一切**：插件路径的解析链是 `UPUP_CODING_AGENT_DIR` → `PI_CODING_AGENT_DIR` → `~/.pi/agent`。OpenBuddy 的 agent 目录是 `~/.openbuddy/agent`，**必须在会话进程里设置前两个之一**，否则 UpUp 会把开关写到 `~/.pi/agent/settings.json`，用户在 OpenBuddy 里看不到、也改不到。
5. **信任策略是"钉死版本 + 白名单来源 + 禁符号链接"**：每个包版本必须与 pin 完全一致（子包 manifest 的 `pi.source` 是 `builtin:upup`，满足 `allowedSources`）；trusted 路径下出现**符号链接直接抛错**——所以可信路径必须是真实目录（`packages/pi-*`），不能是 `node_modules/@upup/*` 那种工作区链接。
6. **会话工具白名单是 1.6.0 下的真正入口**（本轮实测新增）：OpenBuddy 在 `createAgentSession({tools: [...]})` 里写死了一份内建名单，Pi 据此生成 `allowedTools` 匹配器——**任何扩展/包注册的工具都会被过滤掉**，即使扩展已加载、工具已注册。修复见 §0.3.2。
7. **冲突时 UpUp 主动让位，但 OpenBuddy 不在它的扫描范围**：dispatcher 会扫 `<agentDir>/settings.json#packages`、`<agentDir>/extensions/*`、`<agentDir>/npm/node_modules/*` 预计算"已被占用的工具名"，并包裹 `pi.registerTool` 静默跳过。而 OpenBuddy 的包记录在 `pi-settings.json`（不是 `settings.json`），所以**这个让位机制对 OpenBuddy 基本无效**——工具重名必须由我们自己先 diff 出来。

**主线**

- **A 装得上（UP-0 + UP-1）**：可行性实测 → 安装入口 → agentDir 接线 → 官方开关裁剪 → 健康检查 → 升级/卸载。
- **B 看得到（UP-2）**：`pi.app` manifest → `apps_*` → 应用卡。
- **C 管得住（UP-3）**：会话装配合成 + `toolPolicy`（readonly / deny）。
- **D 用起来（UP-4/5/6）+ 收口（UP-7）**：场景、富渲染与专家、推荐与治理、门禁。

## §0.1 关键勘误（上一版说错的地方）

| 上一版说法 | 实际代码 | 影响 |
|---|---|---|
| "UpUp dispatcher 读 `settings.json#packages` 决定挂载哪些子包" | **错**。`resolveConfiguredPiPackages` 只读 env / 项目设置 / 内置白名单；`settings.json#packages` **仅用于冲突扫描** | 裁剪策略从"按子包安装"改为"用 `upupPlugins` 开关"或"显式包清单" |
| "按子包安装即精确裁剪" | **不成立**：即使只装一个子包，dispatcher 仍按自己的三层来源挂载 | 子包粒度安装仍然有用（省磁盘），但不是裁剪手段 |
| "Pi 1.5.2 vs 1.6.0 会让信任策略拒绝" | **不会**：pin 校验只作用于 trusted 路径内的文件（`packageMetadata` 读最近 manifest），核心包 pin 只在资源真的落进核心包时才触发 | 风险降级为**运行时 API 漂移**，由 UP-0 实测确认 |

### §0.3.1 会话不加载扩展/包的根因（已修复）

会话打开时确实一切正常：`extensionsEnabled:true`、`trusted:true`、`noExtensions:false`、`extensionPaths` 与 `packages` 都在、`loader.extensionsResult` 里扩展已加载且 `tools` 已注册（插桩确认：`n:10, tools:7`）。**问题在下一步**：

```ts
// packages/engine/src/session-pool.ts（修复前）
await createAgentSession({
  ...,
  tools: ["read", "bash", "edit", "write", "grep", "find", "ls", "mcp__*", ...builtinToolNames()],
});
```

Pi 把这个 `tools` 数组当作 **`allowedToolNames` 白名单**（`agent-session.js:224 → createToolNameMatcher`），`_refreshToolRegistry()` 会用它过滤 `registeredTools`：

```js
const allCustomTools = [...registeredTools, ...]
  .filter((tool) => this._isAllowedTool(tool.definition.name));
```

所以：**扩展注册了工具，但名字不在白名单里 → 一律被丢弃**。这也解释了为什么 `agent_extensions_inspect` 能看到 `tools: ["probe_xyz"]`、而会话里没有；以及为什么 `/fixture-input` 这类**命令**能跑（命令不经过工具白名单）。

### §0.3.2 修复（UP-3.1 的第一部分）

```ts
// 修复后：扩展已加载 → 把它们的工具名并入白名单；`ob_*` 仍由 extensionsOverride 挡住
const extensionToolNames = [...new Set(
  loader.extensionsResult?.extensions.flatMap((extension) => [...extension.tools.keys()]) ?? [],
)].filter((name) => !name.startsWith("ob_"));

tools: [...内建名单, ...extensionToolNames]
```

安全性没变：扩展加载仍受**两道门控**（`extensionsEnabled` 且目录 `trusted`）；`ob_*` 名字仍被 `reserveBuiltinToolNames` 拒绝；每个工具调用仍走权限门与 `toolPolicy`。

## §3 UpUp 作为 Pi 插件的加载与安装（核心）

### 3.1 加载链路（6 步）

```
1. Pi 读 <upup>/package.json#pi.extensions
      → packages/pi-app/src/pi-plugin-extension.ts（jiti 转译 TS）
2. dispatcher 解析 agentDir（UPUP_CODING_AGENT_DIR / PI_CODING_AGENT_DIR / ~/.pi/agent）
3. dispatcher 解析子包集合：
      env UPUP_PI_PACKAGE_PATHS(+TRUSTED)  >  项目 .upup/settings.json  >  BUILTIN_PI_PACKAGES
4. 把每个子包根注册进 PiPackageCatalog，取回"存在的" extension 绝对路径
5. 逐个子包动态 import 并挂载；技能/prompt 通过 resources_discover 发布
6. 挂载前先包裹 registerTool：已被子包占用的名字静默跳过（冲突让位）
```

**给 OpenBuddy 的含义**：只要 Pi 能 import 第 1 步那个文件，其余全部由 UpUp 自理；OpenBuddy 的权限门仍然对**每一次工具调用**生效（`tool_call` 钩子在最外层）。

### 3.2 agentDir：必须显式接线

| 分辨率 | 值 | 结果 |
|---|---|---|
| 不设 env | `~/.pi/agent` | UpUp 的开关写到 `~/.pi/agent/settings.json`，OpenBuddy 用户不可见 |
| 设 `PI_CODING_AGENT_DIR=~/.openbuddy/agent` | OpenBuddy 的 agent 目录 | 开关与 OpenBuddy 设置同目录，可被应用内 UI 管理 |
| 设 `UPUP_CODING_AGENT_DIR` | 同上（优先级更高） | 推荐，避免与其它 Pi 宿主共用 `PI_CODING_AGENT_DIR` |

**任务**：会话进程启动前设置 `UPUP_CODING_AGENT_DIR`（或 `PI_CODING_AGENT_DIR`）为 `engine.settings.dir`；并确保该目录下有 UpUp 可读的 `settings.json`（只放 `upupPlugins`，与 OpenBuddy 的 `pi-settings.json` 分开）。

### 3.3 裁剪：两条官方路径

| 方案 | 写法 | 优点 | 代价 | 建议 |
|---|---|---|---|---|
| **S1 开关（推荐）** | `<agentDir>/settings.json` → `{"upupPlugins":{"disabled":["@upup/pi-portfolio","@upup/pi-notify","@upup/pi-mobile-host-extension"]}}` | 一行配置；不碰信任策略；可逆 | 只能关 22 个"可插拔"包；基础设施包不可关 | **默认方案** |
| **S2 显式清单** | env `UPUP_PI_PACKAGE_PATHS=…,UPUP_PI_TRUSTED_PATHS=…`，或项目 `.upup/settings.json` 的 `packages` + `upupPiPackages` | 可精确到任意子集；企业可控 | 需自带 pins 与来源白名单；项目文件要求路径在项目内、禁远端 | 高级/企业 |

**推荐的默认 disabled 清单**（S1，命名取目录名）：

```
确定关：pi-portfolio               组合/持仓，涉及账户
        pi-notify                  通知，OpenBuddy 有自己的通知渠道
        pi-mobile-host-extension    手机宿主扩展，OpenBuddy 有自己的手机接入
        pi-openminis-skills-bridge  技能桥，与 OpenBuddy 技能体系重复
待判定：pi-config / pi-cache / pi-management
        —— 它们是别的子包的运行时依赖，关了可能连带失败；由 UP-0.4 实测后再定
```

两条要注意的边界：

- `pi-finance-sdk` **保持启用但 deny 交易工具**。它在可关名单里，关掉更"安全"，但会连 `financial_search` / `calculate_var` 一起丢掉（这两个是常用只读能力）。取舍见 UP-0.6 的清单。
- 基础设施包（`pi-event-adapter` / `pi-observability` / `pi-runtime` / `pi-session`）**不在可关名单**——UpUp 设计上不允许关，关了只会藏掉依赖。

### 3.4 安装源四选一

| 方案 | 命令 | 前提 | 结论 |
|---|---|---|---|
| **A 本地 checkout**（首选验证） | `agent_extensions_install_package({ source: "/Users/…/upup" })` | 仓库已 `bun install`（45 个工作区链接就绪）；jiti 能转译 TS 入口 | M1 走这条 |
| B 本地 tarball | 先 `bun run build` 再打包安装 | 需要构建链 | 分发形态候选 |
| C git 源 | `install_package({ source: "https://github.com/louloulin/upup" })` | 克隆后跑 `npm install --omit=dev`；依赖根 `.npmrc` 的 `legacy-peer-deps` | 只作"用户路径"验证 |
| D 薄包装包 | `@openbuddy/app-invest` 依赖 UpUp，带 `pi.app` | 发布流程 | 长期形态 |

**A 之所以可行**：子包 `exports.default` 指向 `src/index.ts`（`dist` 未构建也不影响解析），根 `node_modules/@upup/*` 已就绪，`require.resolve('@upup/pi-market-data')` 实测解析到源码。

**A 的两个硬约束**：
1. 可信路径必须是**真实目录**（`packages/pi-*`），不能是 `node_modules/@upup/*` 的工作区符号链接——`filesUnder()` 遇到符号链接直接抛错。
2. 子包 manifest 的 `pi.source` 必须是 `builtin:upup`（实测满足），否则内置白名单的 `allowedSources` 校验会失败。

### 3.5 信任策略（会挡住什么）

| 规则 | 触发条件 | 处置 |
|---|---|---|
| 版本必须等于 pin | 文件落在某个 manifest 下且该包在 `pinnedPackages` 里 | 用官方版本；升级时同步改 pin |
| 来源必须白名单 | `pi.source` 不属于 `allowedSources[name]` | 内置路径下为 `builtin:upup`，不要手改 manifest |
| 禁止符号链接 | trusted 路径下任意一级是链接 | 用 `packages/*` 真实目录 |
| 项目级额外要求 | 用项目 `.upup/settings.json` | 必须写 `upupPiPackages.trustedPaths` + `pinnedPackages`，且路径在项目内 |

### 3.6 与 OpenBuddy 的共存：冲突必须自己查

dispatcher 的让位机制只认 **Pi 自己的 `settings.json#packages`**；OpenBuddy 把包记在 `pi-settings.json`，因此 UpUp **看不到** OpenBuddy 已装的扩展与内建工具名。

后果与对策：

- 工具重名（例如 `memory_search`、`read`、`bash`）不会被自动让位 → 可能抛 `Tool "X" conflicts with …`。
- OpenBuddy 已有 `reserveBuiltinToolNames` 保护内建名，但**UpUp 内部工具之间/对 OpenBuddy 其它扩展的重名**没有保护。
- **对策**：UP-0 产出「UpUp 工具名 × OpenBuddy 现有工具名」的差集清单；冲突项在会话装配时用 `extensionsOverride` 或 `pi.app` 的 `toolPolicy.deny` 关掉。

### 3.7 资源通道

- 技能/prompt 由 `resources_discover` 发布，**不写入** `settings#skills|prompts` → UpUp 的约百个技能不会污染用户的全局技能库（这是 UpUp 的隔离设计，对 OpenBuddy 是好事）。
- 因此 OpenBuddy 侧「技能列表」若要看 UpUp 技能，必须从 `resources_discover` 的产物读，而不是 `skills_list` 的全局根。

### 3.8 升级 / 卸载 / 回滚

| 动作 | 命令 | 附加要求 |
|---|---|---|
| 检查更新 | `agent_extensions_check_updates` | — |
| 升级 | `agent_extensions_update_packages` | 升级后必须重跑健康检查（工具集会变） |
| 卸载 | `agent_extensions_remove_package` | 同时清 `upupPlugins` 里对应项与本地 app 记录 |
| 回滚 | 卸载 + 按记录的旧 source 重装 | 记录 `{source, version, toolsDigest}` |

### 3.9 兼容性风险（UP-0 必须回答）

| 风险 | 现象 | 处置 |
|---|---|---|
| 运行时 API 漂移（UpUp 面向 Pi 1.5.2） | jiti 转译或运行时缺 API | 记录首个失败点；必要时锁 Pi 版本或给 UpUp 打补丁 |
| 启动变慢 | 24 个子包全挂 + 现场转译 | S1 关掉不需要的包；记录冷启动；必要时预热 |
| MaxListeners 警告 | UpUp 自述 >10 包订阅同一事件 | 记录；减少子包 |
| 工具重名 | `Tool "X" conflicts` | 见 3.6 |
| 无数据源凭证 | 首轮问答失败 | 默认源降级 + 空态说明 |

### 10.4 术语

| 术语 | 含义 |
|---|---|
| dispatcher | UpUp 的唯一 Pi 扩展入口，负责挂载子包 |
| 子包（`@upup/pi-*`） | 各自带 `pi` 块（tools/extensions/skills/prompts/workflows/policies） |
| `upupPlugins` | UpUp 官方开关，位于 `<agentDir>/settings.json` |
| pin / allowedSources | 信任策略里的"精确版本"与"允许来源" |
| 应用（App） | 带 `pi.app` manifest 的包，有卡片、可整体启停 |
| `toolPolicy` | 应用声明的 readonly / ask / deny，与权限门串联 |
