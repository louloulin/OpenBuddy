# 20261116 — OpenBuddy P2P：本地极致推理 × 节点互为 Agent / LLM Provider

> **日期**：2026-11-14 起草（文件名按约定记为 20261116）**基线**：`feat/electron-pi` @ `76e6fb21`（Electron 45.3.0 + 进程内 `@earendil-works/pi-coding-agent` 1.5.2）
> **目标**：
> 1. 内嵌一个本地推理引擎，性能做到极致，安装后开箱可用。
> 2. 让每台装了 OpenBuddy 的电脑都是一个 **P2P 节点**：可以把自己的**模型（LLM Provider）**和**助手（Agent）**提供给其他 OpenBuddy 节点，也可以使用别人共享的。
>
> **范围**：本文是调研和方案设计，不含代码改动。各条结论标明了来源（§16）；厂商自测的数字一律标「自报」。
> **注意**：`docs/` 在 `.gitignore` 第 32 行。本文件要入库需要 `git add -f`。

## §0 结论先行

1. **本地引擎用 llama.cpp 的 `llama serve` 路由模式，作为独立子进程（sidecar）运行，不嵌进主进程。**
   - 硬件覆盖最广：Metal / CUDA / Vulkan / ROCm / CPU。
   - 路由模式下一个进程管多个模型，按需加载和卸载。
   - 2026-05 合入了多 token 预测（MTP），带 MTP 头的模型（Qwen3.6、Gemma 4）解码快 1.5–2 倍（社区实测）。
   - 原生提供 OpenAI 兼容接口。
   - **Pi 1.5.2 自带 `builtin:llama.cpp` 扩展**（`node_modules/@earendil-works/pi-coding-agent/dist/extensions/llama/`），已经实现了路由模式的模型列表、加载卸载、休眠唤醒和 Hugging Face 下载。但 OpenBuddy 当前用 `noExtensions` 把它一起关掉了（`electron/agent/pi.ts:480`）。**先复用它，不要自己重写。**
   - Jan v0.8.0（2026-05）走的也是"单个 llama.cpp 路由进程 + MTP"这条路线。
2. **Mac 的第二后端是 MLX，排在后期。**
   - MLX 在 Apple Silicon 上的优势：≤14B 的模型解码更快；M5 上能用神经加速器，首 token 更快。
   - Ollama 0.19（2026-03）已把 Apple Silicon 后端切到 MLX。
   - 先把 llama.cpp 做透，MLX 作为第二阶段的可选后端。
3. **不选进程内绑定（node-llama-cpp）。** 原因有三：
   - GPU 驱动一崩溃，会带垮主进程里的 Pi 和全部会话。
   - 要跟着 Electron ABI 重新编译，打包时还要把 asar 解包。
   - llama.cpp 几乎每天发版，升级会被 Electron 的发版节奏卡住。
4. **P2P 网络层用 iroh 1.0**（2026-06-15 发布，承诺线协议稳定）。
   - 官方 Node 绑定是 `@number0/iroh`（napi-rs，带预编译二进制）。
   - 按公钥拨号，底层是 QUIC，打洞失败时走中继兜底。
   - 放在 Electron 的 `utilityProcess` 里运行，原生模块崩了不影响主进程。
   - 中继服务器可以自建，**国内网络必须自建中继**。
5. **两种服务共用一个原语：P2P 流 ↔ 本机回环 HTTP 隧道。**

   | ALPN | 内容 | 宿主侧（host）对接 | 客户侧（guest）对接 |
   |---|---|---|---|
   | `openbuddy/llm/1` | OpenAI 兼容推理 | llama-server | Pi 现成的 `openai-completions` 解析，一行不用改 |
   | `openbuddy/a2a/1` | A2A v1.0 JSON-RPC 任务 | 官方 `@a2a-js/sdk` | 官方 `@a2a-js/sdk` |

   顺带的好处：本机回环端口还能给 Claude Code、Cursor 等外部工具用，效果和 LM Studio 的 LM Link 一样。
6. **v1 只按整个请求路由，不拆分单个模型。**
   - 每个节点跑完整的模型，请求整个转发过去。LocalAI 的 federated 模式、mesh-llm 的默认行为都是这样。
   - 跨广域网拆分模型太慢：prima.cpp 在局域网上跑 70B 也要 674 ms/token。
   - 拆分放进研究轨道（§13 Phase 6），交给 llama.cpp RPC 或 mesh-llm。
7. **默认只在私有圈子里共享，不做公网算力市场。**
   - 用邀请链接或二维码配对（项目已经依赖 `qrcode`）。
   - 每个圈子单独设访问控制和配额。
   - **只共享本地模型。云端 BYOK 的 key 一律禁止共享**：转售或共享 API 访问权限违反大多数厂商的服务条款。
8. **Agent 工作负载以 prefill 为主。**
   - Pi 每轮都会重发系统提示词、工具定义和历史记录，所以本地引擎的优化重点是：前缀缓存、KV 复用、多槽位并行、MTP。不能只盯解码 tok/s。
   - 基准测试要用真实的 Agent 回放，不能用短提示词（§15）。
9. **最接近的开源对标是 mesh-llm**（Block / Mesh-LLM 组织）。它的组合是 iroh + llama.cpp + A2A agents 插件 + blackboard 协作板，还能用 `mesh-llm pi` 直接拉起 Pi。
   - **Phase 0 先做一次互通 spike**：OpenBuddy 能不能作为 mesh-llm 的客户端或节点？
   - 再据此决定**自建**还是**集成**（§14 决策点 D1）。
   - 我们的差异化在桌面端的 Agent 体验、圈子管理和审批 UX，不在分布式张量计算。

**一句话路线**：Phase 0 spike 与选型锁定（1 周）→ Phase 1 本地引擎（2 周）→ Phase 2 P2P 网络与配对（2 周）→ Phase 3 共享 LLM（1.5 周）→ Phase 4 共享 Agent / A2A（2.5 周）→ Phase 5 MLX 后端与打磨（1.5 周）→ Phase 6 研究轨道（模型拆分、公开网络与积分）。**每个 Phase 都有硬验收。**

## §2 调研：可嵌入的本地推理引擎

### 2.1 候选一览

| 引擎 | 形态 | 硬件 | 2026 年的亮点 | 嵌入难度 | 结论 |
|---|---|---|---|---|---|
| **llama.cpp**（ggml-org，现在统一成 `llama` 命令，官网 llama.app） | C/C++ 单个静态二进制，带 OpenAI 兼容服务 | Metal / CUDA / Vulkan / ROCm / CPU | 路由模式（不重启就能加载和卸载模型）；MTP（2026-05-16 合入，PR #22673）；Pi 内置支持 | **低**：作为 sidecar 二进制随包发布 | **主引擎** |
| **MLX / mlx-lm**（Apple） | Python 库和 C++ 核心，有 mlx-c / mlx-swift | 只有 Apple Silicon | ≤14B 模型比 llama.cpp 快 10–20%；M5 上能用神经加速器，首 token 有优势（多为第三方测试，结论有冲突） | 中：要嵌 Python，或基于 mlx-c 自己写服务 | **Mac 第二后端（Phase 5）** |
| vllm-mlx | 基于 MLX 的服务 | Apple Silicon | 连续批处理（16 并发时 3.7–4.3 倍）；前缀缓存加速 5.8 倍（论文自报，arXiv 2601.19139） | 中：Python | 作为 MLX 后端的服务层候选 |
| **mistral.rs** | Rust 库和 OpenAI 兼容服务 | CUDA / Metal / CPU | v0.9.1（2026-08）；v0.8.2 自称在 Gemma 4 上 CUDA 吞吐最高是 llama.cpp 的 2.8 倍（自报） | 中：可以做 sidecar，没有 Node 绑定 | NVIDIA 用户的可选后端，先观察 |
| ik_llama.cpp | llama.cpp 的分支 | 主攻 CPU / 混合 | 融合 MoE 算子，号称 MoE 推理快约 1.9 倍（自报） | 和 llama.cpp 一样 | 进阶选项："自定义引擎二进制" |
| KTransformers | Python + 内核 | CPU（AMX）+ GPU | 把专家层放进内存，单卡就能跑超大 MoE | 高 | 不嵌入。服务器场景可作为外部端点 |
| node-llama-cpp | Node 原生绑定 | 自动选 Metal / CUDA / Vulkan | 有各平台的 GPU 预编译包；在 Electron 里默认不从源码编译，需要把 asar 解包 | 中 | **不选**（理由见 §0.3） |
| Ollama | Go 守护进程 | 全平台；Mac 走 MLX | 0.19 起 Mac 用 MLX；但包装层开销明显（社区测试：原生 llama.cpp 89 tok/s，经 Ollama 只有 43 tok/s） | 要用户自己装 | **只做检测**：本机有就作为外部端点接入 |
| LM Studio（llmster） | 闭源应用和无界面守护进程 | 全平台 | LM Link 远程模型 | 要用户自己装 | 只做检测：`:1234` |
| Microsoft Foundry Local | 进程内 SDK（MIT）+ ONNX Runtime | Windows 为主，可用 NPU | SDK 可以打进应用一起发布，不需要用户装 CLI | 中 | Windows NPU 的后续选项 |
| AMD Lemonade | 本地 HTTP 服务（Apache-2.0） | AMD GPU / NPU，底层是 llama.cpp Vulkan | 一套服务覆盖 GPU、NPU 和多模态 | 中 | 只做检测：`:13305` |
| LiteRT-LM / ONNX Runtime GenAI / MLC LLM / Nexa / Cactus | 端侧框架 | 移动端和 NPU 为主 | 主要面向移动端、浏览器（WebGPU）和高通 NPU | 高 | 桌面端不选 |
| vLLM / SGLang | 服务器级 | 数据中心 GPU | 吞吐最强 | 高，不适合桌面 | 只作为外部端点 |

### 2.2 选型结论与理由

- **llama.cpp 作为 sidecar**：
  1. **崩溃隔离**：llama-server 崩了，只需要重启引擎，会话池不受影响。
  2. **升级解耦**：二进制可以单独热更新，不用等 Electron 发版。
  3. **一个进程管多模型**：路由模式加上 `--models-max`。
  4. **Pi 已有现成实现**：模型列表、休眠和唤醒、加载和卸载、Hugging Face 下载，还有 classifier 能力。
  5. **业界先例**：Jan、Lemonade、Liquid AI 的 Electron 指南都用这种形态。
- **外部端点检测**：启动时探测 `127.0.0.1` 上的 11434（Ollama）、1234（LM Studio）、9931（llama serve 默认端口）、13305（Lemonade）、8000（vLLM）。探测到的作为一键导入的"本机外部引擎"，不重复下载模型。
- **"极致性能"落在这些参数上**（§6.3）：KV 缓存量化、Flash Attention、MTP 或草稿模型投机解码、多槽位、`cache_prompt`、上下文检查点。另外用 Agent 回放基准（§15）自动给出推荐参数，不让用户手调。

## §3 调研：P2P 推理与相关产品

| 项目 / 产品 | 网络层 | 共享粒度 | Agent 层 | 现状 | 借鉴点 |
|---|---|---|---|---|---|
| **mesh-llm**（Mesh-LLM 组织 / Block） | iroh + 自建 gossip（准入、版本兼容、可信节点） | 整个模型优先，放不下才拆分（"skippy" 拆分方式，不同于 llama.cpp RPC） | `agents-plugin`（A2A + MCP）、`blackboard` 协作板；`mesh-llm goose/pi/opencode/claude` 一键拉起 Agent | 活跃；许可证说法不一，需核对 LICENSE | **最接近的对标**：每个节点在 `:9337/v1` 暴露 OpenAI 兼容接口，并按 `model` 字段路由 |
| **LM Studio LM Link** | Tailscale tsnet（用户态 WireGuard） | 整个模型，远程模型标记为"Linked" | 无 | 0.4.6（2026-02-27）发布，6 月扩展到 iPhone | 产品形态：**远程模型和本地模型混在同一列表里**，`localhost:1234` 对外部工具透明；不能把模型推送到远端去下载 |
| **LocalAI P2P** | go-libp2p + EdgeVPN，共享令牌，DHT 加 mDNS | federated 模式转发整个请求；worker 模式拆分（仅 llama.cpp） | 无 | 官方自称"技术预览"；生产环境推荐另一套 NATS + Postgres 方案 | 用令牌入网；`LOCALAI_P2P_DISABLE_DHT` 可限制为只在局域网发现 |
| **exo**（exo labs） | 局域网自动发现；Mac 之间走 Thunderbolt 5 RDMA | 拆分 | 无 | 1.0；需要 macOS 26.2 才有 RDMA，全互联实际只到 4–8 台 | Mac 集群拆分的上限参考 |
| **prima.cpp**（ICLR 2026） | 局域网，基于 llama.cpp | 拆分（piped-ring 流水线 + Halda 调度器） | 无 | 论文和代码 | 家庭集群跑 70B：674 ms/token，比 llama.cpp 快约 15 倍（自报） |
| **distributed-llama** | 局域网 TCP | 张量并行，节点数必须是 2 的幂 | 无 | 2025-09 之后没有新版本 | 拆分方案的限制条件 |
| **Parallax**（Gradient） | Lattica P2P | 异构节点拆分（GPU 用 SGLang，Mac 用 MLX） | 无 | 0.0.x | 两阶段调度 |
| **Petals** | DHT 公网群 | 按 transformer block 分到不同节点 | 无 | BLOOM 时代的项目，假设节点都会合作 | 公网群有可靠性和信任问题 |
| **mycellm** | QUIC + Ed25519 身份 | 整个请求 | 无 | 新项目（2026-04，0.6.x，Apache-2.0） | **积分机制**：做节点赚积分，自己用时消耗积分；每次请求有 Ed25519 签名回执；不用加密货币 |
| **LLMule** | 自建 P2P | 共享 Ollama 模型 | 无 | 桌面客户端 | 隐私提示："网络模型不要发敏感信息" |
| **Symmetry**（twinny） | Hyperswarm，加一个中心服务器分配节点 | 整个请求 | 无 | **2025-12-03 已归档** | 有中心调度器的 P2P 模式维护不下去，可作为反面参考 |
| **Hyperspace** | libp2p、DHT、GossipSub | 推理加其他节点能力 | "分布式 AGI"实验 | 节点规模等多为自报 | 积分和市场的商业模式 |
| Pooled | 浏览器 WebRTC + WebGPU | 拆分 | 面向编程 Agent | 新项目 | 纯浏览器形态 |
| Inference.net（原 Kuzco）、Gonka、FAR Labs 等 | 中心化调度或代币 | 整个请求 | 无 | 商业网络 | 不跟进代币路线 |

**结论**：
- **只做"模型共享"已经有人做了**（LM Link、mesh-llm）。
- **把"Agent 共享"做成桌面端一等公民体验的还没有**：配对、审批、沙箱、成果回传、委派。mesh-llm 的 agents 插件最接近，但它是命令行和网格形态。
- OpenBuddy 应该把重心放在 **Agent 层和圈子 UX** 上。推理网络层尽量用现成方案，或者与现成方案互通。

## §4 调研：网络层与 Agent 协议

### 4.1 传输层

| 方案 | 寻址 | NAT 穿透 | Node / Electron | 风险 | 结论 |
|---|---|---|---|---|---|
| **iroh 1.0**（n0） | 公钥（"按公钥拨号，不按 IP"） | QUIC 打洞，失败走中继 | `@number0/iroh`（napi-rs 预编译；Node ≥20.3；没有 Intel Mac 版） | 原生模块，需放进 utilityProcess；0.35 系列的公共中继支持到 2026-12-31 | **选用** |
| Hyperswarm / HyperDHT（Holepunch） | 公钥 + 主题 | UDP 打洞；DHT 节点同时承担 STUN 和中继的角色 | 纯 JS，成熟（Keet / Pear 在用） | 默认引导节点是 node1–3.hyperdht.org，国内连通性没有验证 | **备选**（iroh 绑定出问题时） |
| js-libp2p | PeerId | 打洞（DCUtR）+ circuit relay | 纯 JS，但依赖面大 | 复杂度高 | 不选 |
| Tailscale tsnet（LM Link 的方案） | Tailnet | DERP | 只有 Go 库，要单独跑 sidecar | 依赖账号和协调服务器 | 不选；高级用户可以直接走自己的 Tailnet，把它当"手动地址"填 |
| WebRTC DataChannel | — | ICE / TURN | 需要 Chromium 或原生库 | 需要信令服务器 | 不选 |

**国内网络**：iroh 的中继协议可以自建（`iroh-relay`），部署在国内云上。设置里提供"中继服务器"选项，默认用 OpenBuddy 自建的国内和海外各一组。局域网内用 mDNS 或本地发现直连，不经过中继。

### 4.2 Agent 协议

- **A2A v1.0**（2026-03-12 发布，当前 1.0.1）：
  - 由 Linux Foundation 下的 Agentic AI Foundation 托管，和 MCP、AGENTS.md、goose 在同一个基金会。
  - Agent Card 默认放在 `/.well-known/agent-card.json`。v1.0 支持签名卡片，每个接口单独声明协议版本。
  - 支持三种绑定：JSON-RPC 2.0、gRPC、HTTP+JSON。
  - 官方 TS SDK 是 `@a2a-js/sdk`（1.1.0）：服务端有 `AgentExecutor` / `DefaultRequestHandler` / `TaskStore`，客户端有 `ClientFactory`；用 SSE 流式推送任务状态和产物；另有 v0.3 兼容层。
- **MCP** 管的是"Agent ↔ 工具"，A2A 管的是"Agent ↔ Agent"。OpenBuddy 已经通过 `@earendil-works/pi-mcp` 接了 MCP。远程 Agent 用 A2A，避免自造协议，**还能和 mesh-llm agents-plugin、goose 等生态互通**。
- **身份**：A2A 的签名卡片原本靠 HTTPS 域名来验证，P2P 场景下没有域名。我们改为**用 iroh 节点公钥签名**：卡片里带上节点 ID，客户侧核对拨号对象的公钥是否与之一致。

## §5 总体架构

```text
┌──────────────────────── OpenBuddy 节点（每台电脑） ────────────────────────┐
│ Renderer：模型选择器（本地 / 好友 / 云端）· 设置 › 本地模型 · 设置 › P2P 圈子 │
│          · 好友助手（专家选择器）· 共享审计日志 · 审批弹窗（远程任务）       │
│                      ▲ window.openbuddy（IPC 契约 + 审计门禁）              │
├──────────────────────┼──────────────────────────────────────────────────────┤
│ Main process         │                                                      │
│  PiEngine（会话池）──┼── Providers ──┬── 用户目录 providers.json（云端 BYOK）│
│    │                 │               ├── LocalEngineSource → 127.0.0.1:LLAMA │
│    │                 │               ├── PeerSource → 127.0.0.1:TUNNEL/p2p/… │
│    │                 │               └── 虚拟模型 auto（本地→好友→云端）       │
│  RemoteTaskPool（独立配额）←─ A2A Host Handler（本机回环，带令牌）          │
│  EngineManager ── spawn ──► llama serve（路由模式，--api-key，127.0.0.1）   │
│        │                    └─ 可选：MLX 后端 / 外部端点（Ollama 等）        │
│  P2PBridge ◄── MessagePort ──► utilityProcess: P2PNode（iroh 1.0）          │
└──────────────────────────────────────────────────┬─────────────────────────┘
                                                   │ QUIC（直连 / 打洞 / 中继）
          ALPN: openbuddy/ctl/1 · openbuddy/llm/1 · openbuddy/a2a/1
                                                   │
                                     其他 OpenBuddy 节点（同构）
```

**一次"用好友模型"的请求**：
1. Pi 以为自己在调用 `http://127.0.0.1:<隧道端口>/p2p/<节点>/v1/chat/completions`。
2. P2PBridge 校验回环令牌，打开到目标节点的 `openbuddy/llm/1` 流。
3. 宿主侧检查访问控制和配额，把请求转给自己的 llama-server。
4. SSE 字节原样流回。

Pi 的流式解析、工具调用解析、思考块解析全部复用，不需要改动。

## §6 本地推理引擎设计

### 6.1 组件

- `electron/services/engine/manager.ts`（`EngineManager`）负责引擎的全生命周期：
  - 定位二进制，用 `--host 127.0.0.1 --port <随机> --api-key <随机>` 启动；
  - 健康检查（`/health`），崩溃后按指数退避重启，连续崩溃就熔断并给出提示；
  - 退出时清理进程；
  - stdout 和 stderr 写进滚动日志。
- `electron/services/engine/hardware.ts`：探测 GPU 型号和显存（Metal 的 recommendedMaxWorkingSetSize、`nvidia-smi`、Vulkan 设备列表）、内存、CPU 指令集、是否接电源。据此生成**推荐档位**。
- `electron/services/engine/library.ts`：管理模型库。
  - 下载 GGUF，支持断点续传和 sha256 校验；
  - 镜像源可选 Hugging Face、hf-mirror、ModelScope；
  - 磁盘配额；按 llama.cpp 路由模式要求的目录结构存放（单文件直接放；多模态和分片的模型各放一个子目录）。
- **复用 Pi 的 `builtin:llama.cpp`**：它已经实现了 `/models` 解析（含 sleeping 状态和 decision 模型识别）、加载和卸载、Hugging Face 搜索和下载。
  - Phase 0 要验证两件事：在 `noExtensions` 的前提下能否通过 `extensionFactories` 单独注入它；它的 `/llama` 交互能否映射到我们的桌面表单（`ExtensionUiBridge` 已经支持 select / confirm / input）。
  - 不行的话，就把 `dist/extensions/llama/{client,huggingface}.js` 的逻辑移植到 `library.ts`。
- `Providers` 新增"动态来源"接口 `ProviderSource { id; list(): RuntimeProviderConfig[]; onChange }`：
  - `sync()` 时把用户目录和所有动态来源合并后再注册；
  - 动态来源有变化时发 `agent://models-update`（`ipc/handlers/agent.ts:229` 已有这个事件）。

### 6.2 二进制分发

| 平台 | 内置版本 | 可选下载版本 |
|---|---|---|
| macOS arm64 | Metal 版（llama.app 安装器本来就只支持 Apple Silicon） | — |
| Windows x64 | Vulkan 版（覆盖 NVIDIA / AMD / Intel） | CUDA 12/13 版（体积大，首次检测到 NVIDIA 显卡时提示下载） |
| Linux x64 | Vulkan 版 + CPU 版 | CUDA 版 |

- 二进制放在 `resources/engine/<platform>/`，并加入 `electron-builder.yml` 的 `asarUnpack`，同时走签名和公证。
- 引擎**可以独立升级**：从 ggml-org 的发布页下载，校验签名，然后原子替换。如果升级后健康检查不过，自动回滚。
- 高级选项："使用自定义 llama-server 二进制"。供 ik_llama.cpp 用户、自编译 ROCm 的用户使用。

### 6.3 性能策略（"极致"在这里）

| 手段 | 参数（以 `llama serve --help` 为准） | 解决的问题 |
|---|---|---|
| 全部层放 GPU，自动适配显存 | `-ngl all` / `--fit` | 不让用户手调 |
| Flash Attention + KV 量化 | `-fa on`，`--cache-type-k/v q8_0` | 长上下文更省显存，Agent 需要 32k 以上 |
| **前缀缓存** | `cache_prompt`（默认开）；`--cache-reuse N` | Pi 每轮重发系统提示词和工具定义，命中缓存后 prefill 接近零 |
| **混合架构的上下文检查点** | `--ctx-checkpoints 32 --checkpoint-min-step 0`（Pi 文档对 Qwen3.5 类混合模型的建议） | 混合模型回退半截缓存时不用整段重算 |
| **MTP 投机解码** | `--spec-type draft-mtp`（Jan 0.8 的预设；需要 b9193 及以上） | 支持 MTP 的模型解码快 1.5–2 倍 |
| 草稿模型投机解码 | `-md <draft>` | 不支持 MTP 的模型的退路 |
| 多槽位 + 统一 KV | `--parallel N --kv-unified` | 本机多会话并行，加上 P2P 来的请求 |
| 路由模式 | `--models-max K`，`--no-models-autoload` | 内存够就同时驻留多个模型，比如一个聊天模型加一个小的分类模型 |
| 工具调用 | `--jinja` | Agent 必须有 |
| 休眠 | 路由模式的 sleeping 状态 | 空闲时释放显存，选中时自动唤醒 |

- **自动调参**：首次加载模型时，跑一次 §15 的 Agent 回放微基准（约 30 秒）。在候选组合（槽位数、KV 类型、MTP 开或关）里选 P50 首 token 最短、同时解码速度不低于 90% 的组合，写进该模型的预设。
- **推荐模型**：只推荐**工具调用可靠**、并且带 MTP 头的模型（例如 Qwen3.6、Gemma 4 系列），按显存分三档。模型卡上标出"适合 Agent / 只适合聊天"。

### 6.4 外部引擎

- 检测到的 Ollama、LM Studio、Lemonade、vLLM 显示为"本机外部引擎"卡片，一键导入成厂商（填 baseUrl，再调已有的 `providers_fetch_models`）。
- 不托管它们的生命周期。

## §7 P2P 网络层设计

### 7.1 身份

- 每个节点一对 Ed25519 密钥，即 iroh 的 SecretKey，节点 ID 就是公钥。私钥存在 safeStorage。没有钥匙串时，降级为"每次启动生成临时身份"，同时**关闭共享，只保留作为客户使用**，并提示原因。
- 显示名和头像由用户设置，写进签名的节点卡片。**节点 ID 才是唯一可信的标识**，显示名可以重复，会标出指纹前 6 位。

### 7.2 圈子与配对

- **圈子**：一组互相信任的节点，例如"我的设备"、"团队 A"。每个节点可以加入多个圈子。
- **邀请**：
  1. 生成 `openbuddy://join?c=<圈子ID>&n=<发起方节点ID>&r=<中继提示>&t=<一次性令牌>&exp=<过期时间>`，同时生成二维码。
  2. 被邀请方用它拨号，在 `openbuddy/ctl/1` 上完成令牌校验和双向签名。
  3. 双方各自记下对方的节点 ID。
- 令牌只能用一次，默认 24 小时过期，可以撤销。
- **"我的设备"快捷方式**：同一个用户的多台电脑，在局域网发现后点一下就能确认配对。
- **撤销**：从圈子里移除某个节点后，立即断开它的连接，以后的连接直接拒绝。
- 圈子成员表由**每个节点本地保存**，没有中心服务器。v1 由圈主同步（圈主下线时成员表只读）；v2 再考虑基于 gossip 的 CRDT。

### 7.3 发现与连接

- **局域网**：iroh 的本地发现（mDNS 类机制）。
- **广域网**：用圈子里已知的节点 ID 拨号，地址解析交给 iroh 的发现服务和中继。
- **在线状态**：在 `ctl` 流上每 15 秒发一次心跳，内容是可用模型、负载（槽位占用、队列长度）、是否接电源、是否允许接活。
- **节点卡片**：签名的 JSON，内含节点 ID、显示名、版本、`llm.models[]`（含上下文长度、是否支持工具和图像、量化方式、估计速度）、`agents[]`（A2A Agent Card 的摘要）、配额策略摘要。

### 7.4 隧道（核心原语）

```text
guest：Pi/外部工具 ─HTTP→ 127.0.0.1:T（令牌 Bearer）─→ P2PBridge ─QUIC stream(ALPN)→
host ：P2PNode ─→ 访问控制 / 配额 / 审计 ─→ 127.0.0.1:目标服务（只允许 llama-server 或 A2A 处理器）
```

- 宿主侧**只转发到白名单里的服务**（`llm` 只转给 llama-server 的 `/v1/chat/completions`、`/v1/models`；`a2a` 只转给 A2A 处理器）。永远不转发任意端口。路径和方法都按白名单过滤。
- 每个 QUIC 流承载一个 HTTP/1.1 请求和它的响应，SSE 原样透传。客户端断开时，宿主侧马上取消上游请求，llama-server 也会因为连接关闭而停止生成。
- 回环端口只绑定 `127.0.0.1`，令牌每次启动随机生成。是否允许外部工具使用，由"对外暴露给本机其他应用"开关控制，默认关。

### 7.5 进程模型

- `P2PNode` 跑在 `utilityProcess.fork()` 里，iroh 的原生模块只在这个进程加载。它和主进程之间用 MessagePort 通信，消息有类型并做校验，校验方式同 `validatePayload`。
- 它崩溃时，主进程会把它重新拉起，并发出 `p2p://status` 事件。已有的会话不受影响；进行中的远程请求按"网络错误"处理，交给 Pi 的重试机制。

## §8 共享 LLM Provider

### 8.1 宿主侧（host）

- 设置项（在每个圈子上单独设）：
  - 共享哪些本地模型；
  - 并发上限（默认 1，即一个槽位）；
  - 每个节点每天的 token 上限；
  - 每次请求的最大上下文和最大输出；
  - 时间窗口（例如只在夜间）；
  - "只在空闲时"（本机没有会话在运行）、"只在接电源时"；
  - 本机用户优先：发现本机有请求排队时，远程请求的新 token 会被暂停或拒绝。
- **只共享本地引擎和本机外部引擎。云端 BYOK 的 key 不可共享**：UI 里不提供这个选项，代码里硬性拒绝。
- 审计日志：记录时间、节点、模型、token 数、耗时、结果。**默认不记录提示词内容。**

### 8.2 客户侧（guest）与 Pi 集成

- 每个在线并且共享了模型的节点，都会成为一个动态厂商：`p2p:<短ID>`，api 是 `openai-completions`，baseUrl 指向隧道，模型元数据来自节点卡片。
- 模型选择器分三组：**本地 / 好友节点 / 云端**。好友模型上标出节点名、延迟、估计速度，并显示隐私徽标"内容对 TA 可见"。
- 节点离线时：
  - 它的模型标为不可用，不从列表里删除，避免会话里记录的模型身份失效；
  - 正在进行的请求，交给 Pi 已有的重试和 `agent://retry` 事件处理。
- **虚拟模型 `auto`**：通过 Pi 的 `registerVirtualModel`（`docs/virtual-models.md`）注册。
  - 按"本地引擎 → 在线好友（按延迟和负载排序）→ 云端默认模型"的顺序选第一个可用的；
  - 同时检查上下文窗口和能力（工具、图像）是否满足；
  - Pi 会在每条 assistant 消息里记下实际用的物理模型，可以追溯；
  - 这是"开箱即用"的核心体验：用户不用知道模型具体在哪台机器上跑。

### 8.3 计量（v1）

- 不做结算。双方各自记账：宿主侧记"我为谁跑了多少"，客户侧记"我用了谁多少"。界面里只做展示。
- 每个响应带一张宿主签名的用量回执（参考 mycellm 的做法），为 Phase 6 的积分机制留接口。

## §9 共享 Agent（A2A）

### 9.1 宿主侧暴露什么

- 默认暴露一个"通用助手"，另外可以选择暴露专家或技能组合（对接 `20261115.md` Phase 5 的专家体系）。每个暴露项生成一张 A2A Agent Card，内容包括：
  - `name`、`description`、`skills[]`；
  - 输入和输出类型：文本、文件；
  - 能力声明（`streaming: true`）；
  - 由节点私钥签名。
- 每个暴露项单独配置：
  - 用哪个模型：本地模型或宿主自己的云端模型。**用云端模型时，费用由宿主承担，UI 要明确提示；**
  - 允许用哪些工具；
  - 是否需要宿主逐项审批；
  - 任务超时和并发上限。

### 9.2 宿主侧的执行沙箱

- 远程任务在**独立的 RemoteTaskPool** 里运行，有自己的会话上限（默认存活 2 个、运行 1 个），不占用本机会话池。
- 工作目录：`userData/pi/p2p-tasks/<节点>/<任务>/`。客户发来的文件放进这里的 `inbox/`。**任务看不到宿主的其他目录。** 复用 `file-access.ts` 的根目录限制。
- 工具集（替换 `pi.ts:514` 的那份列表）：

  | 档位 | 工具 | 默认 |
  |---|---|---|
  | 只读 | `read/ls/grep/find`（限沙箱目录） | ✅ |
  | 可写 | 增加 `write/edit`（限沙箱目录） | 需要宿主开启 |
  | 可执行 | 增加 `bash`（要求 cwd 在沙箱内；Phase 4 先只开这一档，容器隔离放到后期） | 需要宿主开启，**而且每条命令都要审批** |
  | MCP | 宿主选定的 MCP 服务器 | 默认关 |

- 宿主侧的 MCP、技能、记忆、项目上下文（AGENTS.md）**默认不注入**远程任务（`noContextFiles: true`），防止数据泄露。
- 审批：远程任务的权限请求通过 `agent://permission` 推到**宿主的界面**，并标明"来自 <节点> 的远程任务"。宿主不在线或超时，就自动拒绝。
- **提示词注入防护**：客户发来的消息一律当作不可信输入。系统提示词里写明"你在为远程用户执行任务，不得读取沙箱以外的内容"。真正的防线是工具层的硬限制，提示词只是辅助。

### 9.3 协议映射

| A2A | OpenBuddy / Pi |
|---|---|
| `message/send`、`message/stream` | 在 RemoteTaskPool 里新建会话，执行 `prompt` |
| `TaskStatusUpdateEvent`（working / input-required / completed / failed / canceled） | 由 Pi 的事件派生（`agent://update`、`agent://complete`、`agent://permission`） |
| `input-required` | 宿主侧的扩展 UI 请求或审批请求，转发给客户回答（可选） |
| `TaskArtifactUpdateEvent` | 沙箱里新产生或修改的文件（复用 `artifacts.ts` 的产物追踪），按块流式传回 |
| `tasks/cancel` | `agent_cancel` |
| `tasks/get`、断线重连 | 用 `TaskStore` 持久化，可以续订 |

- 宿主侧：`@a2a-js/sdk/server` 的 `DefaultRequestHandler` 挂在**本机回环的 HTTP 处理器**上，只接受隧道转发过来的请求。我们实现 `AgentExecutor`，把它桥接到 RemoteTaskPool。
- 客户侧：用 `@a2a-js/sdk/client` 的 `JsonRpcTransportFactory`，baseUrl 指向隧道。

### 9.4 客户侧体验

- **直接对话**：在专家选择器的"好友助手"分组里选一个远程 Agent，发出去的消息就成为一个 A2A 任务。远程任务的过程（状态、工具摘要、产物）在本地的 TurnView 里渲染成一个"远程任务卡"。
- **委派**：注册一个 Pi 扩展工具 `delegate_to_peer(agent, task, files[])`，本地 Agent 可以把子任务派给好友的 Agent，适合"我的轻薄本把编译或长任务交给台式机"这类场景。这个工具本身需要本地审批，因为它会把文件发出去。
- 产物传回后放进本地会话的产物区，和本地产物用同一套 UI 和 checkpoint 机制。

### 9.5 "我的设备"是杀手场景

同一个用户的多台设备（笔记本 + 台式机 GPU + 家里的 Mac Studio）组成默认圈子，对它们放开**可写和可执行档位**（仍然限在沙箱里）。这样笔记本就能：
- 直接用台式机上的大模型；
- 把需要 GPU 或长时间运行的任务派到台式机上执行。

这是 LM Link 只做到一半（只能共享模型）的东西。

## §10 安全与隐私

| 威胁 | 对策 | 剩余风险 |
|---|---|---|
| 宿主能看到客户的提示词 | UI 上明确标出"内容对 TA 可见"；默认只在私有圈子里使用；敏感会话可以锁定"只用本地或云端模型" | 没有 TEE 就做不到机密推理，这是 P2P 共享的本质限制 |
| 宿主谎报模型（拿小模型冒充大模型） | 只在信任圈子里使用；节点卡片带量化信息；可选抽检：同一个提示词交叉比对（Phase 6） | 无法验证 |
| 客户滥用宿主资源 | 配额、槽位、时间窗口、本机优先、熔断；按节点限流；可以一键踢出 | — |
| 客户通过提示词注入攻击宿主 Agent | 沙箱目录 + 受限工具 + 逐条审批 + 不注入宿主上下文 | 只读档位下，只能读到沙箱里客户自己传来的文件 |
| 冒充节点 | 节点 ID 就是公钥，QUIC 握手时校验；节点卡片和 Agent Card 都签名；显示名不可信，一律附上指纹 | — |
| 邀请链接泄露 | 一次性、会过期、可撤销；加入时圈主可以选择要求确认 | — |
| 本机其他进程冒用回环端口 | 只绑定 127.0.0.1，随机令牌，对外工具开关默认关 | 同一用户下的恶意进程本来就能做更多事 |
| 共享云端 key 违反服务条款 | 代码里硬性禁止 | — |
| 模型许可证 | 节点卡片显示模型的许可证，共享前提示用户 | 用户自己负责 |
| 原生模块崩溃或漏洞 | iroh 放在 utilityProcess 里；llama-server 是独立进程；二进制做签名校验 | — |

**审计**：宿主侧的"共享日志"页面列出每一次远程 LLM 请求和 Agent 任务，并可以导出。远程 Agent 执行的每条工具调用都要进日志，作为证据。

## §13 分阶段计划（每个阶段都有硬验收）

### Phase 0 · Spike 与选型锁定（1 周）
- 0.1 在 Electron 45 的 `utilityProcess` 里加载 `@number0/iroh`：两台机器（一台在 NAT 后、一台走中继）建流、回声、测吞吐和 RTT。
- 0.2 自建 `iroh-relay`，分别部署在国内和海外，测国内网络下的直连率和中继延迟。
- 0.3 验证 `builtin:llama.cpp` 能否在 `noExtensions` 的前提下注入；把它的 `/llama` 交互映射到桌面表单。
- 0.4 **mesh-llm 互通 spike**：OpenBuddy 能否直接把 mesh-llm 节点的 `:9337/v1` 当作厂商使用？OpenBuddy 节点能否加入 mesh？据此做决策 D1（§14）。
- 0.5 跑 llama.cpp 和 MLX 的 Agent 回放基准，各在一台 Mac 和一台 NVIDIA 机器上（方法见 §15）。
- 0.6 清理 `packages/collaboration/*` 的遗留目录。
- **验收**：一份 spike 报告，包含 iroh 直连和中继的延迟与吞吐、国内连通率、基准数据，以及 D1 和 D2 的决定。

### Phase 1 · 本地推理引擎（2 周）
- 1.1 EngineManager：启动、健康检查、崩溃重启、熔断、日志。
- 1.2 打包：mac Metal 版、win Vulkan 版内置；CUDA 版按需下载；asarUnpack 和签名。
- 1.3 硬件探测和推荐档位；模型库（下载、续传、校验、镜像源）。
- 1.4 Providers 支持动态来源，"本地"组接入模型选择器。
- 1.5 性能预设：`--jinja`、Flash Attention、KV 量化、`--parallel`、前缀缓存、MTP；自动调参的微基准。
- 1.6 外部引擎检测和导入。
- 1.7 设置 › 本地模型页面。
- **验收**：
  - 新装的 mac-arm64 和 win-x64 不用填任何 URL 或 key，就能下载推荐模型，并完成一次**带工具调用**的 Agent 任务（读文件、改文件），有截图；
  - 手动 `kill -9` llama-server，5 秒内自动恢复，会话不丢；
  - 同一模型、同一参数下，吞吐不低于直接跑 llama-server 的 95%；
  - Agent 回放第 2 轮及以后的首 token 时间，比关掉 `cache_prompt` 时至少低 60%；
  - 新命令全部通过 `pnpm audit:ipc`，单测覆盖 manager 和 library 的状态机。

### Phase 2 · P2P 网络与配对（2 周）
- 2.1 身份（存 safeStorage，没有钥匙串时降级）；节点卡片的签名和校验。
- 2.2 P2PNode 运行在 utilityProcess；P2PBridge 用 MessagePort 通信；`ctl` 协议（心跳、卡片、圈子操作）。
- 2.3 圈子、邀请（链接和二维码）、加入、撤销、"我的设备"在局域网内一键配对。
- 2.4 隧道原语，加宿主侧的服务白名单。
- 2.5 设置 › P2P 页面；`p2p://peers` 实时更新。
- **验收**：
  - 两台不在同一网络的机器，用二维码加入同一个圈子，60 秒内互相显示在线；
  - 撤销后对方立即断开，重连被拒绝；
  - 伪造节点卡片（改显示名、换公钥）会被拒绝；
  - 隧道无法访问白名单以外的端口或路径（单测 + 渗透用例）；
  - utilityProcess 被 kill 后自动恢复。

### Phase 3 · 共享 LLM Provider（1.5 周）
- 3.1 宿主侧：共享策略、配额、本机优先、审计日志；硬性禁止共享云端 key。
- 3.2 客户侧：动态厂商 `p2p:<id>`、模型选择器的"好友"组、隐私徽标、离线降级。
- 3.3 虚拟模型 `auto`（本地 → 好友 → 云端）。
- 3.4 签名的用量回执；双方各自记账的展示。
- 3.5 可选：回环端口对外部工具开放（默认关）。
- **验收**：
  - 笔记本（没有 GPU）用台式机的本地模型完成一次带工具调用的 Agent 任务；
  - 局域网内的首 token 额外开销低于 30 ms；广域网中继下低于 1 个 RTT 加上中继的转发开销；
  - 吞吐不低于宿主本机的 95%；
  - 宿主本机发起会话时，远程请求按策略暂停或拒绝；
  - 中途拔网线，Pi 显示重试，恢复后能继续；
  - 配额用完返回可读的中文错误。

### Phase 4 · 共享 Agent / A2A（2.5 周）
- 4.1 RemoteTaskPool：独立的会话池、沙箱目录、受限工具集、不注入宿主上下文。
- 4.2 A2A 宿主：Agent Card 生成和签名，`AgentExecutor` 桥接，TaskStore 持久化。
- 4.3 审批流：宿主界面上的远程任务审批和通知，超时自动拒绝。
- 4.4 产物回传（分块流式），客户侧的远程任务卡。
- 4.5 "好友助手"出现在专家选择器里；`delegate_to_peer` 工具（需要本地审批）。
- 4.6 "我的设备"圈子的可写和可执行档位。
- **验收**：
  - 客户把一个仓库压缩包发给"我的设备"里的台式机 Agent，请它跑测试并修复，最后拿回 diff 产物，有截图；
  - 远程任务尝试读取 `~/.ssh`、执行沙箱外的命令，都被拒绝，并记入审计（这一组做成测试用例）；
  - 客户取消后，宿主 2 秒内停止；
  - 与第三方 A2A 客户端（官方 `@a2a-js/sdk` 示例客户端、mesh-llm agents-plugin）互通：至少完成一次收发。

### Phase 5 · MLX 后端与打磨（1.5 周）
- 5.1 根据 D2 的结论接入 MLX 后端（vllm-mlx 或基于 mlx-c 自写的服务），只在 Apple Silicon 上作为可选后端，自动调参时和 llama.cpp 一起比较。
- 5.2 Windows 的 NPU 路线评估（Foundry Local 或 Lemonade 作为外部端点）。
- 5.3 首次使用引导：首启时提示"下载本地模型"或"加入好友圈子"。
- 5.4 文案、空状态、错误码中文化；深色模式检查。
- **验收**：M 系列 Mac 上，对 ≤14B 的模型自动选到更快的后端，回放基准有数据；整体真机走查截图。

### Phase 6 · 研究轨道（不排期）
- 6.1 **模型拆分**：在局域网的"我的设备"里，用 llama.cpp RPC（`rpc-server`）把超大模型拆到多台机器上跑；或者集成 mesh-llm 的 skippy 拆分，或 prima.cpp。
- 6.2 **公开网络和积分**：参考 mycellm 的签名回执和积分（不用代币），加上信誉和抽检，把节点开放给陌生人。需要单独做一次风险评审。
- 6.3 圈子成员表改为基于 CRDT 的多主同步。
- 6.4 移动端作为客户（类似 LM Link 扩展到 iPhone 的做法）。
- 6.5 机密推理：调研能否在消费级硬件上用 TEE。

## §14 决策点与风险

| 编号 | 决策 | 选项 | 默认倾向 | 何时决定 |
|---|---|---|---|---|
| D1 | 推理网络自建还是集成 mesh-llm | A：自建 iroh 隧道（本方案）；B：内置 mesh-llm sidecar，只做 UI 和 Agent 层；C：自建，同时兼容 mesh-llm 协议 | **A，保留 C**。原因：mesh-llm 的许可证待核实；它是 Rust 写的完整网格，粒度比"私有圈子"粗 | Phase 0 结束 |
| D2 | Mac 上的 MLX 后端用什么形态 | vllm-mlx（Python，有连续批处理和前缀缓存）/ 基于 mlx-c 自写 / 不做 | 先看 0.5 的基准；**Agent 回放提升不到 20% 就不做** | Phase 0 结束 |
| D3 | Windows 默认用 Vulkan 版还是 CUDA 版 | Vulkan 覆盖面广；CUDA 在 NVIDIA 上更快 | 内置 Vulkan，检测到 NVIDIA 时提示下载 CUDA | Phase 1 |
| D4 | 宿主暴露 Agent 时允许用云端模型吗 | 允许（费用由宿主承担）/ 只允许本地 | 允许，但默认关，并显示费用提示 | Phase 4 |

**风险**：
- **iroh 的 Node 绑定还不成熟**：1.0 才发布 5 个月。缓解：Phase 0 先验证；隧道层留一层抽象，必要时换成 Hyperswarm。
- **国内网络**：公共中继和 DHT 引导节点可能连不上。缓解：自建中继，局域网优先直连。
- **llama.cpp 发版快、参数会变**：MTP 的参数名就已经有 `--mtp`、`--spec-type mtp`、`--spec-type draft-mtp` 几种写法。缓解：锁定经过验证的构建号；预设按构建号做版本管理；升级前在 CI 里跑回放基准。
- **安装包体积**：每个平台增加约 30–200 MB（CUDA 版最大）。缓解：只内置最小的后端，其余按需下载。
- **模型的 Agent 能力不够**：小模型的工具调用不稳定。缓解：只推荐验证过的模型；`auto` 根据能力标签回退到更强的模型。
- **法律和条款**：云端 key 共享已经禁止；模型许可证由用户确认；公开网络放到 Phase 6 单独评审。

## §15 指标与基准方法

- **Agent 回放基准**：从真实会话里导出 10 段典型的 Pi 交互（系统提示词、工具定义、多轮工具调用，上下文 8k–48k），按原节奏重放，测：
  - 每轮首 token 时间（P50 / P95），**第 1 轮和后续轮分开统计**；
  - prefill 的 tok/s、decode 的 tok/s；
  - 工具调用解析成功率；
  - 峰值显存和内存。
- **P2P 指标**：
  - 直连率和中继率；
  - 建流延迟；
  - 额外的首 token 开销（隧道 vs 本机回环）；
  - 吞吐损失；
  - 断线恢复时间。
- **体验指标**：
  - 从全新安装到第一次本地 Agent 任务成功的时间（目标 ≤10 分钟，下载时间单独计）；
  - 从邀请到对方可用的时间（目标 ≤60 秒）。
- 不拿短提示词的 tok/s 做结论。各来源的数字很多是厂商自测，互相矛盾，**一律以本项目回放基准为准**。
