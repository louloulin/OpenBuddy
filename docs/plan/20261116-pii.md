## §0 结论先行

**一句话**：OpenBuddy 的"对话 + 产物"已经接近第一梯队。WorkBuddy 的另外四根支柱是**专家、连接器、自动化、记忆**，它们目前只有界面没有后端。而实现它们需要的能力，**Pi SDK 和它自带的示例扩展里几乎都现成**；旧 Tauri 后端还留着可以移植的数据结构和调度算法。本计划把这三处的东西接到新架构上，并把所有假入口改成真的或者藏起来。

**1. 现在在哪**（§2）

- **对话与产物**：重新核对后，UI 计划的 U4.9"+"菜单、U4.6 上下文分项、U2.4"同时还原文件"都比记录的更接近完成。真正的空白是这几项：
  - 分支切换 ‹1/2›
  - `!命令`
  - `@` 引用文件
  - 扩展、技能、连接器的管理
  - 多窗口与快速唤起
- **产品面**：
  - 侧栏的 6 个一级入口被 `App.tsx:415` 拦成 toast。
  - "专家·技能·连接器"面板可以绕过拦截打开：入口是输入框里的"管理连接器 →"（`App.tsx:1005,1021`）。但面板调用的 21 个目录命令（`experts_*`、`connectors_*`、`skills_catalog_*`）后端都没有实现。
  - "策略设置"的规则从来没有生效过：`checkPolicy`（`features/settings/policy-engine.ts:95`）没有任何调用方。
  - 设置里有 4 个分区不可达。
- **架构**：
  - P1 搬家已完成。host 已经按模块拆开，engine 已经按 feature 拆开。
  - `host_capabilities` 能报告宿主真实提供的命令（`dcdd92d1`），但**渲染层还没用它**，入口的显隐仍是硬编码。

**2. 能力盘点**（§3，"发掘"的结果）

**3. 核心判断：WorkBuddy 的每根支柱都能落到 Pi 原语上，不用另造运行时**（§4 有完整的映射表）

| WorkBuddy 能力 | 落到哪个 Pi 原语 |
|---|---|
| 专家 | `preset` 的模型、思考档位、工具集，加上 `before_agent_start` 追加人设，绑定关系写进会话条目 |
| 子代理 / 专家团 | 会话池里的**子会话**，由内置扩展注册 `subagent` 工具。不照搬示例里"另起一个 pi 进程"的做法 |
| 计划与进度 | `plan-mode`，加上 `todo` 的"状态存在工具结果里"模式；切换分支后状态自动正确 |
| 自动化 | 主进程调度器 + 会话池的后台会话 + 现有的审批和通知 |
| 记忆 | 文件存储 + `before_agent_start` 注入 + 后台会话整理 |
| 连接器 | pi-mcp + 按服务管理的 OAuth + 工具级规则；工具多时用 `tool-search` 延迟暴露 |
| 安全中心 | 现有的 `tool_call` 权限门 + `protected-paths` 规则 + `permission_save` |

**4. 地基只有三块**（W0）

- **按能力显隐**：渲染层读 `host_capabilities`，再加 FeatureRegistry（承接 md-R1 / R8）。后端没实现的入口自动不出现。此后每接通一个模块，它的入口就自己出现。
- **SDK 设置落盘**：把 `inMemory({})` 换成 OpenBuddy 自己管理的设置层。开放自动压缩、自动重试、队列模式、收藏模型和内置扩展开关。
- **内置扩展通道**：新目录 `packages/engine/src/builtin/*`，放主进程提供的可信 `ExtensionFactory`。它们**不受**"用户扩展"总开关和目录信任的影响，和现在的权限门、检查点、MCP 同级。专家、待办、子代理、记忆、交接都从这里接入。

**5. 北极星**：**WorkBuddy 的每个入口都是真的，背后都是 Pi 原语；后端没有的入口不出现。**

**6. 顺序**（§6）

W0 地基 → W1 补完对话 → W2 专家·技能·连接器 → W3 计划·待办·子代理 → W4 自动化与后台 → W5 记忆·资料库·项目 → W6 安全中心与设置重排 → W7 窗口与唤起 → W8 本地模型入口。

- W1 和 W2 可以并行。
- W4 依赖 W0.4 的设置层和 W3.4 的后台子会话。
- W5 的记忆注入依赖 W0.5 的内置扩展通道。
- 粗估：单人约 14 周，两人并行约 8 周。**W0 + W1 + W2（单人约 6 周）是"Pi 版 WorkBuddy"的最小可交付版本**，之后每个阶段都可以单独发布。

### 4.3 一次完整任务（总验收用的走查脚本）

1. 首页选专家"数据分析师"。输入框出现专家 chip；模型和思考档位按专家预设切换，工具集按专家限制。
2. 选"想一想"后发送。代理只读探索，回答末尾给出计划；右上角"任务概览"显示 5 个步骤。
3. 点"按此计划执行"，切回"做一做"。代理调用 `ob_todo` 更新步骤，概览逐项打勾。需要读 Excel 时，代理派出子代理"表格读取"：子代理卡片在回合内流式显示，结束后回传摘要和用量。
4. 代理要用"企业邮箱"连接器，但还没授权。输入框上方出现"需要连接 企业邮箱 [连接]"，授权后自动继续。
5. 写出 `report.md`，回合里出现产物卡片。不满意就点"重新生成"，回合出现 ‹ 1/2 ›，两个版本可以来回看，文件也可以随分支一起还原。
6. 点"保存为自动化"，表单预填提示词、专家、连接器、工作空间和权限。设为每周一 9:00。
7. 周一 9:00 时窗口已关闭：应用在托盘常驻，后台会话照常运行；需要审批时发系统通知；完成后消息中心和运行记录里各有一条，点开就是那次的会话。
8. 记忆里多了一条"周报格式偏好"，下次任务自动带上；它在设置里可见、可删。

这 8 步全部在真机上跑通，是本计划的总验收（§7）。

## §5 架构落点规则：每一项新能力都按这五段走

> 依据 `20261115-md.md` §5.1–§5.3。新代码不得让边界检查（`tools/check-boundaries.mjs`）的任何一类计数增长。

| 段 | 放什么 | 规则 |
|---|---|---|
| ① `packages/protocol` | 命令名进 `commands.ts`，事件进 `events.ts`；DTO 放各自的类型文件，**不再往 `dto.ts` 里加**；载荷校验进 `validate.ts` | 渲染层已在用的旧名一律沿用，实现后从 `PENDING_COMMANDS` 移出；`contract-gate.test.ts` 必须通过 |
| ② `packages/host/src/modules/<模块>.ts` | 一个 `HostModule`，只做参数整理和调用。新模块：`experts`、`automation`、`memory`、`library`、`projects`、`usage` | 每条命令都有校验的正反例（md-P3.3）；`host_capabilities` 会自动包含新命令 |
| ③ `packages/engine` / `packages/services` | 会话相关的放 `engine/src/features/*.ts`（第一个参数是 `EngineContext`）；**内置扩展放 `engine/src/builtin/*.ts`**；与会话无关的存储和调度放 `services/src/<域>/` | 禁止依赖 `electron`、DOM、react。存储以后走 md-R2 的仓储接口；R2 完成之前，新存储**各用一个独立的 JSON 文件**，不再往 `openbuddy.json` 里加 |
| ④ `packages/client` | 新命令的类型化调用放 `api/<模块>.ts`。这是 md-R5 的目标结构，新代码直接按它写 | 组件不直接 import `@/lib/ipc` |
| ⑤ `apps/web/src/features/<feature>` | 界面；在 FeatureRegistry 里声明 `requires` | feature 之间只经各自的 `index.ts` 依赖，并遵守 md §5.2 的 feature 依赖表 |

**内置扩展**（`engine/src/builtin/`）的约定：
- **形态**：每个都是一个 `ExtensionFactory`，注册在 `session-pool.ts` 的 `extensionFactories` 里，排在权限门和检查点之后。
- **开关**：**不受** `extensionsEnabled` 和目录信任的影响（它们是应用自己的代码），但每个都可以在设置里单独关闭（W0.4 的设置层）。
- **命名**：注册的工具统一加 `ob_` 前缀（如 `ob_todo`、`ob_subagent`），避免和用户扩展冲突，并且要加进 `tools` 白名单（`session-pool.ts:83`）。
- **状态**：优先存在会话条目里（S7，或工具结果的 `details`），这样分叉、切换分支、重新生成之后状态自动正确。只有跨会话的数据（专家、记忆）才存文件。
- **事件**：只给渲染层发**瘦身后的事件**，沿用 `event-pipeline.ts` 的做法，不发完整的状态快照。

## §8 风险与对策

| 风险 | 对策 |
|---|---|
| 子代理把会话池占满，挤掉前台任务 | 子会话单独限额；前台会话优先；有运行中子代理的父会话不被淘汰 |
| 内置扩展和用户扩展冲突：同名工具，或者同一个钩子都在改系统提示词 | 工具名加 `ob_` 前缀；内置扩展排在用户扩展之前；人设和记忆以"追加"方式改系统提示词，不整体替换 |
| SDK 设置落盘后，与 OpenBuddy 自己的 `openbuddy.json` 职责重叠 | 写清分工：会话行为（压缩、重试、队列、收藏模型）归 `pi-settings.json`；应用和安全相关的（权限、信任、通知）留在原处，等 md-R2 的仓储统一 |
| 自动化在无人值守时做出危险操作 | 默认权限沿用任务配置；"完全访问"的自动化在保存时二次确认；自动化里的删除类命令一律拒绝，不可配置 |
| 示例扩展随 Pi 升级而变化 | 只借模式，不 import 示例文件；升级 Pi 时跑一遍引擎集成测试 |
| 连接器目录的质量问题：模板过期，或者需要的 CLI 没装 | "添加"后必须通过"测试连接"才显示为已连接；模板注明最低版本 |
| md-R2 / R5 / R7 还没完成，按目标结构写的新代码会和旧结构并存 | 新命令一律走 `client/api/<模块>.ts`；新存储一律用独立文件；不碰 `agent-client.ts` 的旧导出，等 R5 统一处理 |
| 计划范围太大 | W0 + W1 + W2 是最小可交付版本；从 W4 起每个阶段都能单独发布 |

#### 10.1.15 第 12 轮：产物尾项（W1.9 前四项，2026-11-17）

- **文件树随产物刷新（U1.8）**：`FileTreeView` 新增 `refreshKey`（来自 `artifacts` 的 version）。变化时清空缓存并重读根目录 + 所有已展开目录，agent 新写出的文件无需折叠再展开即可出现；首次挂载不重复请求。面板关闭（Workbench 卸载）时不计算。
