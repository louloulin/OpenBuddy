## §0 结论先行

**一句话**：OpenBuddy 的功能面已经接近第一梯队，**单用户桌面版达到"内部试点 / 设计伙伴 Beta"标准**；但**公开 GA 还差发布工程、可观测性、错误恢复、国际化/无障碍和性能预算**这五块。

**生产判定**

| 使用方式 | 判定 | 说明 |
|---|---|---|
| 个人本地使用（自带 API Key） | ✅ 可试点 | 核心链路完整、真机 E2E 通过、安全不变量成立 |
| 小团队内部试用（各自安装） | ◐ 有条件 | 缺签名/更新/崩溃上报/统一诊断，支持成本高 |
| 公开下载 GA | ✗ 未达 | 无签名公证、无自动更新、无错误边界、无 i18n/a11y 基线 |
| 团队 SaaS / 多租户 | ✗ 未达 | `apps/server` 尚未实现，无 SSO、租户隔离、审计 |
| 受监管企业 | ✗ 未达 | 缺合规审计、策略下发、数据留存/删除流程 |

**综合分：约 74 / 100（Beta）**。功能 92、质量门禁 86、安全 82，但可观测 30、发布分发 40、i18n/a11y 35 拉低整体。

**三个必须先解决的 P0**

1. **可分发**：代码签名 + macOS 公证 + 自动更新 + 回滚 + 灰度。
2. **可诊断**：React ErrorBoundary、主进程崩溃捕获、结构化日志与日志轮转、可选崩溃上报。
3. **可恢复**：全量数据备份/恢复、schema 版本与迁移、损坏文件自愈、导出全部用户数据。

## §3 P0 阻塞项（发布前必须完成）

### P0-1 可分发：签名、公证、自动更新、回滚

- **现状**：`electron-builder.yml` 中 macOS `notarize: false`；CI 显式 `CSC_IDENTITY_AUTO_DISCOVERY=false`；依赖里没有 `electron-updater`；无更新通道与回滚。
- **要做什么**
  - macOS Developer ID 签名 + notarytool 公证 + stapling；Windows Authenticode 签名。
  - `electron-updater`（或自建更新源）+ 差分包 + 更新前检查运行中任务。
  - 灰度：内部 → 5% → 25% → 100%，每档有停止条件。
  - 回滚：保留上一个可用版本；更新失败自动回退并上报。
  - 设置 · 关于：版本、通道、检查更新、更新日志。
- **验收**：在干净 macOS / Windows 机器上安装并自动升级一次；断网/磁盘满/权限不足三种失败场景可恢复；回滚演练通过。

### P0-2 可诊断：错误边界、崩溃捕获、结构化日志

- **现状**：渲染层无 ErrorBoundary（grep 0 处）；主进程 13 处 `console.*`；无 `crashReporter`/Sentry；诊断报告需用户手动触发。
- **要做什么**
  - 根级 + 路由级 ErrorBoundary：展示可恢复界面（重载 / 导出诊断 / 返回首页），保留当前草稿。
  - 主进程 `uncaughtException` / `unhandledRejection` / `render-process-gone` 统一捕获；写入滚动日志（按大小/日期轮转，默认 7 天）。
  - 日志分级 + 脱敏（路径、Key、`Bearer`、邮箱）；与现有 `diagnostics` 合并成一份可复制的诊断包。
  - 可选崩溃上报（默认关闭、明确授权、含隐私说明）。
- **验收**：注入渲染层异常与主进程异常各一次，界面可恢复且日志/诊断包完整；诊断包中无密钥与绝对路径。

### P0-3 可恢复：备份、schema 版本、损坏自愈

- **现状**：`JsonStore` 使用临时文件 + rename，写入原子；但无 schema 版本、无迁移、无自动备份；`settings` 读取遇到损坏 JSON 会抛错（仅 ENOENT 回退）。
- **要做什么**
  - `openbuddy.json` / `providers.json` / `projects.json` / `automations.json` / `mcp.json` 增加 `schemaVersion` 与顺序迁移。
  - 首次启动与每次升级前做一次快照（保留最近 3 份）；损坏时自动改用最近可用快照并提示。
  - 设置 · 数据管理：一键导出全部用户数据（会话、配置、项目、记忆、自动化），一键恢复。
  - 密钥文件不可用（无钥匙串）时给出明确降级/退出策略，不静默丢 Key。
- **验收**：人为破坏每个 JSON 后应用能启动并恢复；升级迁移幂等；导出包可在另一台机器恢复。

### P0-4 发布流程：多平台、依赖安全、构建可复现

- **现状**：`release.yml` 只有 macOS/Windows 打包，`pnpm test` 后直接 `dist`；无 Linux；无依赖漏洞扫描/SBOM；移动端 CI 独立、非发布阻塞。
- **要做什么**
  - CI 增加 Linux 打包与三平台 E2E 冒烟（至少启动 + 首页 + 一轮对话）。
  - `pnpm audit` / OSV 扫描 + SBOM（CycloneDX）；高危阻断。
  - 锁定 Node/pnpm/Electron 版本；构建产物哈希与来源记录。
  - 发布说明模板 + 升级注意事项；移动端是否随桌面发布单独决策。
- **验收**：三平台流水线绿；高危漏洞 0；从 tag 到产物的构建可复现（哈希一致）。

### P0-5 性能预算：冷启动、首 token、内存、包体

- **现状**：主 chunk 1.1 MB（gzip 347 KB），mermaid 726 KB、katex 517 KB 已分包；无预算与 CI 门禁；冷启动/长会话未测。
- **要做什么**
  - 定义预算：冷启动 p95 ≤ 2.5 s；首 token p95（云端）≤ 3 s；空闲内存 ≤ 400 MB / 长会话 ≤ 800 MB；首屏 JS gzip ≤ 400 KB；交互 INP p95 ≤ 200 ms。
  - 为 mermaid/katex/cytoscape 做按需加载与懒渲染；大文件预览分块。
  - CI 增加 bundle 体积门禁；`stress.js` 纳入每周或发布前跑。
- **验收**：预算写入 CI；连续 3 次长会话压测无内存增长失控；冷启动达标。

> **建议顺序**：P0-2 → P0-3 → P0-1 → P0-5 → P0-4。可观测与恢复先做，才能在签名/更新上线后快速定位问题。

### 4.2 对标 WorkBuddy：差距在"生态与运营"，不在核心能力

**OpenBuddy 领先或持平**
- 本地优先与可离线：本地模型、文件记忆、项目目录、MCP 自托管。
- 可审计的工程结构：monorepo、协议/宿主/引擎分层、边界门禁、1648 项测试、真机 E2E。
- 自动化深度：文件触发、后台会话、托盘常驻、运行中面板。
- 连接器"诚实"：只列可安装的真实 MCP 模板，而不是营销卡片。

**主要差距**
1. **生态与市场**：无插件市场后端、无模板/专家商店、无评分与安装量。
2. **协作**：无共享会话、评论、团队空间、权限继承。
3. **企业能力**：无 SSO/SCIM、审计日志、策略下发、用量配额中心。
4. **上手与内容**：缺新手引导、场景模板、示例工作区、视频/文档。
5. **发布与支持**：无自动更新、崩溃上报、状态页、支持工单闭环。
6. **设计一致性**：功能页页头、导航转场、空态插画、品牌语气尚未统一。

### 4.3 对标 Grok Bot：差距在"完成度与节奏感"

**OpenBuddy 领先或持平**
- 桌面代理能力：真实文件/命令/MCP/审批，而非仅聊天。
- 本地数据与隐私：请求可不出本机；诊断本地生成。
- 长任务：计划、子代理、后台自动化、运行中面板。

**主要差距**
1. **视觉完成度**：统一页头、⌘K 背景压暗 + 缩放、视图切换过渡、空态插画。
2. **节奏与反馈**：流式打字节奏、工具步骤折叠动画、审批卡入场、错误恢复的文案与动效。
3. **首屏体验**：首页场景卡与输入框的层级、引导性还不如 Grok 的"一眼可用"。
4. **移动端打磨**：手势、分享、无障碍与弱网体验仍在推进。
5. **品牌**：图标、插画、语气、截图规范尚未形成系统。

### 4.4 对标 Muse：需要先做产品校准

**事实**：本仓库与本次评估没有 Muse 的可信资料；无法负责任地断言其具体功能。以下为**待校准维度**，不是结论：

- 定位：创意/设计向工作台，还是通用代理？
- 产物形态：画布/多模态/演示稿/视频，还是文件与代码？
- 协作：多人实时编辑、评论、版本？
- 模型策略：自带模型、云托管、混合？
- 分发：Web 优先、桌面优先、移动优先？
- 商业化：订阅、席位、用量、企业版？

**建议的调研协议（1 周内可完成）**
1. 用同一组 8 个任务（写作、数据分析、代码修复、演示稿、调研、自动化、连接器、移动审批）各跑一遍。
2. 记录：完成时间、人工干预次数、产物质量、失败恢复、导出能力、价格。
3. 截图归档到 `docs/plan/bench-20261118-muse/`，只记录可复现事实。
4. 产出一页差距表，替换本文的 `?`。

### 15.1 对 WorkBuddy 的实测结论（2026-11-18，本机 WorkBuddy 5.11.3 / `WorkBuddy.app`）

- WorkBuddy 是 Electron 应用（`Contents/Resources/app.asar`）；专家包由主进程 `connector-harness-marketplace.js` 的 `ExpertPackageManager` 处理，`share.exportZip` / `import.fromPath` / `import.fromUrl` 走同一套格式。
- 真实专家包（`~/.workbuddy/plugins/marketplaces/my-experts/plugins/upup-investment-team.zip`）结构：

```text
<plugin>/.codebuddy-plugin/plugin.json   # 名称、版本、agents[]、expertType、teamInfo、displayName、members、tags、quickPrompts、avatar、categoryId
<plugin>/settings.json                   # { "agent": "<lead id>" }
<plugin>/agents/*.md                     # YAML front matter (name/description/displayName/profession/maxTurns) + 人设正文
<plugin>/avatars/*.png
```

- 自定义专家索引位于 `~/.workbuddy/experts/custom/<account>/experts.json`（专家 id 列表）；内置目录为 `~/.workbuddy/app/cache/experts/manifest.json`。
- 结论：WorkBuddy 的 agent Markdown 与 OpenBuddy 的 `agents/<id>.md` 高度同源，差异主要在 `plugin.json` 元数据、本地化字段、头像与团队结构。

## §16 实施进度（2026-11-18 第六轮：UI 对标 WorkBuddy）

**本轮目标**：用 WorkBuddy 5.11.3 的真实渲染样式校准 OpenBuddy 的"壳"——统一页头、页签字号/间距、控件高度与页面转场；不改变信息架构。

### 16.1 对 WorkBuddy UI 的实测（REA/静态 CSS）

- WorkBuddy 市场页的头部是 **52px 高的 topbar**（`padding: 0 24px`，`-webkit-app-region: drag`），页签是 **18px / 500 的文本页签**（`.um-header__tabs` `gap: 24px`），激活态仅加粗到 600 并使用主文本色，没有胶囊底色（`unified-market-header`）。
- 控件高度以 **32px / 8px 圆角** 为主（搜索、次级按钮）；资料库/自动化等页面复用同一套文本页签语言。
- OpenBuddy 已使用 WorkBuddy 的 `--wb-*` 设计令牌（mint 品牌色、灰阶、语义色），本轮只校准结构与尺寸，不重造调色板。
