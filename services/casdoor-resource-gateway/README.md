# Casdoor Resource Gateway

This service is the production counterpart of OpenBuddy's local enterprise resource registry. It stores tenant-scoped project, knowledge-base, and storage-connection metadata, validates Casdoor OIDC access tokens, applies resource/action authorization, and writes append-only audit records.

## Run

For a production deployment, validate the env file before starting containers. The
check does not print secrets, create containers, or contact Casdoor/New API:

```sh
../../scripts/validate-production-compose.sh .env.production
```

```sh
pnpm install
pnpm run build
CASDOOR_ISSUER=https://casdoor.example.com \
CASDOOR_CLIENT_ID=openbuddy \
RESOURCE_GATEWAY_DATA_DIR=/var/lib/openbuddy-resource-gateway \
node dist/index.js
```

The gateway exposes `GET /healthz`, `GET /readyz`, `GET /metrics` (Prometheus exposition; no auth, no PII), the client-compatible endpoints under `/v1/tenants/:tenantId/resources`, tenant governance endpoints under `/v1/tenants/:tenantId/policy`, `/v1/tenants/:tenantId/runtime-policy`, `/v1/tenants/:tenantId/runtime-usage`, and `/v1/tenants/:tenantId/audit`, the emergency member revocation endpoints under `/v1/tenants/:tenantId/member-revocations` and `/v1/tenants/:tenantId/member-revocations/:subject`, and the tenant observability endpoints under `/v1/tenants/:tenantId/health` and `/v1/tenants/:tenantId/audit-export`, the session binding registry under `/v1/tenants/:tenantId/sessions` and `/v1/tenants/:tenantId/sessions/:sessionId`, the integer OpenBuddy credit ledger under `/v1/tenants/:tenantId/credits`, and the WeKnora token exchange/introspection endpoints under `/v1/token-exchange/weknora` and `/v1/token-exchange/weknora/introspect`. It accepts `Authorization: Bearer <access-token>` and never logs the token. Every response includes an `x-request-id` for support and centralized tracing.

WeKnora exchange requires one explicit Casdoor permission: `weknora.platform.admin`, `weknora.workspace.read`, `weknora.workspace.contribute`, `weknora.workspace.admin`, or `weknora.workspace.owner`. Tenant membership alone and the generic `isAdmin` claim do not grant WeKnora access. Introspection rechecks the Gateway revocation store and tenant authorization version on every call, so member revocation and Casdoor role/permission/organization changes can reject an issued exchange token before its five-minute expiry.

Tenant governance:

- `GET /policy` requires `tenant.policy.read` (or an administrator claim) and returns the active/suspended state and resource quota.
- `GET /runtime-policy` is available to an authenticated tenant member and returns the effective model/MCP allowlists, kill switch, and token quota.
- `GET /credits` and `GET /credits/ledger` return the current member's balance and immutable billing history. Tenant administrators can use `POST /credits/grant` for authorized grants only; `purchase` is rejected and can only be created by a verified payment callback for a billing order. OpenBuddy's trusted main process uses `POST /credits/reserve` followed by `POST /credits/settle` or `/credits/release`. All amounts are integer points and all mutations require an idempotency key.
- Grants and paid plans may set `validDays`/`pointsValidDays`. The source ledger stores `expiresAt`; `POST /credits/expire` is safe to run from a daily Worker or administrator action, expires only unreserved points in FIFO order, and records an idempotent `expire` entry with `sourceLedgerId`. AI reservation also runs the same convergence step before checking available balance.
- A scheduled Worker or tenant billing administrator can call `POST /v1/tenants/:tenantId/credits/expire?all=true` to converge every personal account and shared wallet in one tenant. The response reports `expired`, `accounts`, `wallets`, and subscription `entitlementsExpired`; `all=true` cannot be combined with `subject` or `walletId`. This is the recommended daily expiry job, while the subject and wallet scoped forms remain available for targeted operations.
- Production scheduling should use `scripts/credit-expiry-worker.mjs` and `POST /internal/v1/credits/expire` instead of storing a Casdoor user token in systemd. The worker requires an explicit bounded `CREDIT_EXPIRY_TENANT_IDS` list, `Idempotency-Key`, a fresh timestamp, and HMAC-SHA256 with `RESOURCE_GATEWAY_CREDIT_EXPIRY_SECRET`; missing lists, stale signatures, and idempotency conflicts fail closed.
- The same expiry convergence applies to shared-wallet AI reservations. Wallet expiry entries retain `walletId`, so a team wallet's balance, ledger, and reconciliation statement remain aligned and expired team points cannot fund a model request.
- A registration/orchestration service may call `POST /credits/welcome` with only `{subject, idempotencyKey}`. The Gateway takes the amount and validity from the active zero-price `free` plan, permits one welcome grant per tenant subject, and rejects reuse of an idempotency key belonging to a normal administrative grant. This endpoint does not create Casdoor users or organizations; it is called only after the identity/tenant workflow has completed and must be audited by the caller.
- For an optional closed loop, set `RESOURCE_GATEWAY_AUTO_WELCOME=true` together with an explicit comma-separated `RESOURCE_GATEWAY_AUTO_WELCOME_ORGANIZATIONS` allowlist. A signed Casdoor webhook using either the gateway test shape (`type=user`, `action=add`) or Casdoor's native Record shape (`action=add-user`, `organization`, `user`, `object`) then issues the same deterministic welcome grant. The allowlist is mandatory; the feature is disabled when it is empty. Webhook retries are safe because the key is derived from tenant and subject, and the endpoint is rate-limited; replay responses identify `issued: false`. Do not enable this for invitation/member events until the product's anti-abuse policy explicitly allows invited members to receive free credits.
- Credits are OpenBuddy's product billing unit. Casdoor access tokens remain identity credentials and New API tokens remain gateway credentials; neither is exposed as or substituted for the OpenBuddy credit balance.
- Billing orders are idempotent and remain pending until a verified signed callback marks them paid, failed, or cancelled. A `paid` callback must include both a payment transaction ID and payment channel; the pair is unique so replaying it against another order cannot grant points twice. Pending orders past `expiresAt` are automatically marked `expired` when billing APIs are accessed; late paid callbacks are rejected without granting points.
- `POST /v1/tenants/:tenantId/credits/reconciliation/import` accepts up to 1000 tenant-scoped New API cost records per request. It is intended for an independent reconciliation Worker, requires HMAC via `RESOURCE_GATEWAY_NEW_API_COST_IMPORT_SECRET` outside development, and is idempotent by `tenantId:importKey`. New records must declare `costBasis` as `provider-reported`, `provider-reported-quota`, or `configured-pricing`; legacy records without a basis remain visible as `unknown` and never count as verified external cost. New API's internal `quota` is never interpreted as currency; `provider-reported-quota` means the Worker verified the instance `QuotaPerUnit` before converting it to USD.
- `POST /v1/tenants/:tenantId/ai/chat/completions`, `/ai/completions`, `/ai/responses`, `/ai/embeddings`, `/ai/rerank`, and `/ai/moderations` are controlled New API proxies. Configure `NEW_API_BASE_URL` and either the default `NEW_API_TOKEN`/`NEW_API_GROUP` pair or the production `NEW_API_GROUP_TOKENS_JSON` secret map from New API Group to dedicated service Token. A tenant Group without a mapped Token is rejected instead of silently using another Group's credential. The proxies validate tenant status, kill switch, model allowlist, daily token quota, reserve points, forward OpenAI-compatible JSON, and settle from real New API `usage`; upstream errors release the reservation. Protocol availability is channel-specific: a proxy route being implemented does not mean every New API channel supports it. For example, the verified MiniMax channel supports Chat Completions but returns `unsupported relay mode` for Completions/Embeddings/Rerank and `not implemented` for Responses. Moderations is implemented as a non-streaming input-usage path but remains commercially disabled until each target channel is verified. Completions, Responses, and Moderations streaming remain disabled because their usage/stream settlement contract is not covered.
- When New API explicitly reports `unsupported relay mode` or `not implemented`, the gateway returns `501 NEW_API_PROTOCOL_UNSUPPORTED` after releasing the reservation. The channel/model/protocol acceptance rules are documented in `docs/new-api-channel-capability-matrix.md`; use that matrix rather than inferring capabilities from `/v1/models`.
- `NEW_API_ALLOW_ESTIMATED_USAGE=1` is an explicit compatibility override. The production default rejects successful New API responses without real usage as `NEW_API_USAGE_REQUIRED` and releases the reservation; do not enable the override for financial settlement unless the business has approved estimated billing.
- AI idempotency claims and completed response bodies are persisted in the configured Resource Store. PostgreSQL/MySQL support cross-replica CAS ownership and replay; JSON is single-replica only, and `RESOURCE_GATEWAY_AI_REPLAY_MAX_BYTES` limits replay storage.
- AI requests without an idempotency header receive a server-generated request key. If a caller supplies `idempotency-key` or the legacy `x-idempotency-key`, the value must be 8-160 characters matching `[a-zA-Z0-9_.:-]`; supplying both with different values or supplying a malformed value returns `400 INVALID_AI_IDEMPOTENCY_KEY` before any reservation or New API request, so client retries cannot silently become separately billable calls.
- The AI proxy records the effective New API Group plus optional `x-openbuddy-agent` and `x-openbuddy-session` headers in the server-side ledger. These headers are metadata only; tenant authorization and the Group still come from the verified Casdoor context and tenant policy.
- `GET /v1/tenants/:tenantId/ai/models` is the matching model discovery proxy used by the desktop runtime. It injects the server-side New API credential and tenant Group, then filters upstream models through `modelAllowlist`; the renderer never receives the New API credential.
- `POST /runtime-usage` accepts a bounded additive `{ "tokens": number }` delta from an authenticated tenant member (OpenBuddy sends it only from the trusted Electron main process) and returns the updated daily usage; the service persists it per tenant and UTC date. It cannot read or modify any other tenant resource.
- `PATCH /policy` requires `tenant.policy.write`; include the current `version` as `expectedVersion` for optimistic locking. A stale version returns `TENANT_POLICY_VERSION_CONFLICT` (HTTP 409). The JSON body may contain `{"expectedVersion":3,"status":"active"|"suspended"|"archived","maxResources":1000,"modelAllowlist":["openai/gpt-4o"],"mcpAllowlist":["filesystem"],"killSwitch":false,"maxTokensPerDay":1000000,"newApiGroup":"enterprise"}`. Set `newApiGroup` to an empty string to fall back to the gateway's `NEW_API_GROUP`.
- A suspended tenant cannot list, create, update, or delete resources and returns `TENANT_SUSPENDED` with HTTP `423`.
- An archived tenant is soft-deleted: resources remain readable for audit/export, while writes and runtime usage return `TENANT_ARCHIVED` with HTTP `423`. Archiving and restoring require global admin or `tenant.lifecycle.write`; no irreversible deletion is exposed by this gateway.
- Resource creation is rejected with `TENANT_QUOTA_EXCEEDED` when the tenant reaches `maxResources`.
- `GET /audit?limit=100` requires `tenant.audit.read` and returns only the current tenant's sanitized audit events.
- `GET /member-revocations` and `PATCH /member-revocations/:subject` require `tenant.lifecycle.write` (or a platform administrator). The list is limited to authorized lifecycle administrators and returns only subject, timestamps, and the sanitized reason; PATCH accepts `{"revoked":true|false,"reason":"..."}`. This is an auditable emergency deny-list layered on top of Casdoor membership; it does not replace Casdoor's organization/user directory, and restoration is only possible for an authorized administrator. A global administrator can restore access even when its own subject is listed.
- `GET /healthz` returns adapter-level storage health (kind/latency/error) and process readiness so Kubernetes liveness/readiness probes can fail over multi-replica deployments.
- `GET /metrics` exposes Prometheus text-format counters: `openbuddy_gateway_uptime_seconds`, `openbuddy_gateway_store_kind`, `openbuddy_gateway_http_requests_total{path}`, `openbuddy_gateway_http_outcomes_total{path,outcome}`, `openbuddy_gateway_rate_limited_total`, `openbuddy_gateway_webhook_accepted_total`, `openbuddy_gateway_webhook_rejected_total`, `openbuddy_gateway_audit_events_total`. No tenant identifiers or PII are emitted; pair with the gateway health endpoint for dashboards.

## Distributed tracing

The gateway implements [W3C Trace Context](https://www.w3.org/TR/trace-context/):

- Incoming `traceparent` headers are parsed and validated (zero-filled trace/span ids and malformed flags are rejected, and a fresh trace is minted).
- The parsed context is bound to the request via `AsyncLocalStorage` so audit events, SIEM sinks, downstream HTTP calls and background queues carry the same `traceId` without sprinkling arguments through every call site.
- Every response includes `traceparent` (echoed or freshly minted) and `x-trace-id` (128-bit hex). The same fields are persisted in JSON / Postgres / MySQL audit records.
- The OpenBuddy main process forwards its own `traceparent` header on every CasdoorResourceBackend call so the desktop session and the gateway share one trace.
- `GET /v1/tenants/:tenantId/health` returns the tenant's policy summary, resources by type, revoked-member count, store health and active SIEM sink for monitoring and dashboards; the caller must be a tenant member (active or admin).
- `GET /v1/tenants/:tenantId/audit-export?format=jsonl|csv&since=ISO&limit=N` returns sanitized audit events for SIEM ingestion. The caller must hold `tenant.audit.read`; the response is delivered as `application/x-ndjson` or `text/csv` with a downloadable filename.
- Tenant policies and member revocations are stored atomically beside the resource registry; older registry schema versions are normalized and migrated on read.

Production requirements:

- Put the service behind TLS and an authenticated reverse proxy or private network.
- Use a durable volume for `RESOURCE_GATEWAY_DATA_DIR` and back up `resources.json` and `audit.jsonl` according to retention policy.
- Set `CASDOOR_AUDIENCE` when the access token audience is different from `CASDOOR_CLIENT_ID`.
- The gateway expects a signed JWT access token; if Casdoor issues opaque access tokens, put a trusted introspection adapter in front of it instead of disabling signature validation.
- A tenant `admin` role grants administrative actions only after the JWT also proves membership in that tenant; only an explicit Casdoor `isAdmin` claim can cross tenant membership boundaries.
- Configure `RESOURCE_GATEWAY_MAX_BODY_BYTES`, `RESOURCE_GATEWAY_MAX_RESOURCES`, and `RESOURCE_GATEWAY_AUDIT_MAX_BYTES` for the deployment's quota and retention policy.
- Configure `RESOURCE_GATEWAY_DEFAULT_TENANT_MAX_RESOURCES` to set the initial per-tenant quota; administrators can later tune each tenant through the policy endpoint.
- The default in-memory rate limit is 120 requests per 60 seconds per source address. Tune it with `RESOURCE_GATEWAY_RATE_LIMIT_REQUESTS` and `RESOURCE_GATEWAY_RATE_LIMIT_WINDOW_MS`; use a shared reverse-proxy limit for multiple replicas.
- Storage backends are pluggable via `RESOURCE_GATEWAY_STORE=json|postgres|mysql|memory`. JSON is the development default (atomic JSON with rename + bounded JSONL audit log). Production deployments set `RESOURCE_GATEWAY_STORE=postgres` and `POSTGRES_CONNECTION_STRING=postgres://...` or `RESOURCE_GATEWAY_STORE=mysql` + `MYSQL_CONNECTION_STRING=mysql://...`; the gateway uses database-specific placeholders, JSON types, upserts, indexes, affected-row handling, and a monotonic `resource_state.revision` compare-and-swap so multi-instance state writes cannot silently overwrite a newer ledger. The production Docker build enables both SQL drivers with `INCLUDE_SQL_DRIVERS=true`.
- When started with `NODE_ENV=production`, the gateway fails closed unless SQL persistence, a non-empty `NEW_API_GROUP_TOKENS_JSON` Group→dedicated-token map, `NEW_API_CAPABILITIES_JSON`, webhook/payment/back-channel HMAC secrets, and New API cost-import HMAC are all configured. Production also rejects estimated usage settlement; every billable AI response must include real upstream usage.
- SQL bootstrap adds `resource_state.revision` for existing installations; the migration is additive and safe to rerun. SQL-backed reads do not use a long-lived process cache, and a compare-and-swap conflict causes the gateway to reload the newest state and replay the bounded mutation rather than overwrite another replica's update. Use Postgres/MySQL as the billing source of truth; JSON remains single-replica development storage.
- Audit events can be mirrored to a SIEM via `RESOURCE_GATEWAY_SIEM=syslog|webhook|csv` and the matching `RESOURCE_GATEWAY_SIEM_ENDPOINT`/`RESOURCE_GATEWAY_SIEM_FILE`; failures are dropped so the gateway never blocks on a SIEM outage.
- `Dockerfile` and `docker-compose.example.yml` provide a non-root single-replica baseline. Put TLS, backup, secret-free environment injection, and an authenticated reverse proxy in front of it.
- `POST /v1/webhooks/casdoor` accepts signed (HMAC-SHA256 over the JSON body) Casdoor webhook deliveries for `user.update`/`user.delete`, `organization.delete`, and `group`/`role`/`permission` updates. Set `RESOURCE_GATEWAY_WEBHOOK_SECRET` to enable; without it the endpoint returns `WEBHOOK_DISABLED` (503). Each delivery is forwarded to the audit log and SIEM sink; the gateway never blocks on a webhook flood because rate limiting still applies.
- The full request/response contract is published as OpenAPI 3.1 in `services/casdoor-resource-gateway/openapi.yaml`. Render with Swagger UI / Redoc / Stoplight or feed straight to SDK generators for external governance integrations.
- `POST /v1/token-exchange/weknora` is an optional internal bridge: it accepts a valid Casdoor bearer token and returns a five-minute, tenant-bound WeKnora token signed with `RESOURCE_GATEWAY_WEKNORA_EXCHANGE_SECRET`. Keep the endpoint private, configure the same secret and issuer/audience in WeKnora, and never send refresh tokens to it.
- `scripts/new-api-capability-snapshot.mjs` is a read-only deployment gate for New API management drift. It snapshots status, groups, channels, models, and optionally log-stat metadata without returning or persisting secrets; set `NEW_API_EXPECTED_GROUPS`, `NEW_API_EXPECTED_MODELS`, and `NEW_API_EXPECTED_CHANNELS` to fail closed when a required execution capability disappears.
- The OpenBuddy main process can also push webhooks back to Casdoor via `casdoor:webhook-deliver` (renderer hook + HMAC-SHA256 signature using `OPENBUDDY_CASDOOR_WEBHOOK_SECRET`); the Settings panel exposes a "模拟 Casdoor webhook" button so admins can exercise the round trip locally.

## Production deployment

- `docker-compose.production.yml` ships a 3-service stack: Postgres 16, the resource gateway, and Caddy 2 for TLS termination. Only Caddy exposes 80/443; the gateway listens on the internal Docker network. `.env.production.example` enumerates the required environment variables.
- Build the gateway image with SQL drivers enabled: `docker build --build-arg INCLUDE_SQL_DRIVERS=true -t openbuddy-resource-gateway .`. Without the flag the image stays slim and relies on the JSON store, suitable for CI / preview.
- Health checks rely on `/readyz`; the Caddyfile uses `{$GATEWAY_DOMAIN}` so the same compose file can be re-used across staging / production.
- Rotate `RESOURCE_GATEWAY_WEBHOOK_SECRET` and `POSTGRES_PASSWORD` through your secret manager; never commit them to git.
- `POST /v1/tenants/:tenantId/audit-archive?before=ISO` requires `tenant.lifecycle.write` and rotates audit events older than the cutoff into an archive file (JSON adapter) or archived table (Postgres/MySQL); returns the count archived and remaining. Use it from a scheduled job to enforce retention policy before SIEM ingestion.
- Rate limits use the store adapter so multi-replica deployments share the sliding window via Postgres/MySQL atomic upserts. Single-replica JSON adapter persists counters to `rate-limit.json` so restarts keep the budget.

## Session binding registry

Each OpenBuddy session (desktop session, web session, automation, team, ephemeral) is registered against the gateway so that tenant administrators can audit who is currently signed in and force-logout a session. The gateway stores `sessionId -> { tenantId, subject, kind, scopes, startedAt, lastSeenAt, endedAt?, metadata? }` in the same store adapter as resources and audit events (JSON / Postgres / MySQL / in-memory). The same authorization model applies: a member can only register sessions bound to their own subject; tenant admins or `isAdmin` tokens can register sessions for any subject in the tenant. Deleting the session emits a `session.unregister` audit event so SIEMs can correlate with force-logout workflows. The `/health` endpoint exposes `activeSessions` for dashboards, and `/metrics` will count session lifecycle events once that instrumentation lands.
